# EP3D 升級計畫

寫於 M17.12 之後。這份文件回答一個問題：**接下來做什麼，為什麼是這個順序。**

排序的依據不是「哪個功能最顯眼」，而是**哪個缺口正在讓其他東西做不了**。
一個被十件事等待的地基，比十件事本身值錢。

---

## 先看清楚：這個專案真正的問題是什麼

M17 這一輪連續出現的缺陷有一個共同形狀，值得先講，因為它會影響下面每一階段怎麼做。

| 缺陷 | 兩邊各自正確的東西 |
|---|---|
| Pad 的長度改了沒反應 | 面板建了列；`ApplyPropertyEdit` 會寫入。中間的 `field` 沒人比對 |
| 面上開草圖沒有投影 | kernel 讀了邊界；投影會投影。中間的手抄漏了一個欄位 |
| Fillet 說 created 但沒圓角 | kernel 正確拒絕；指令有 `describeCreatedFeature`。這兩個沒接上 |
| Pad 樹上顯示 Failed 而非 Blocked | `stateOf` 正確；`rollUp` 正確。吸收讓它們第一次相遇 |
| `featuresReferencingSketch` 只列 Pad | 每個 feature 都對；那份清單沒跟上 |

**沒有一個是「某段程式碼寫錯」。每一個都是「兩個東西必須一致，而各自的測試都不會發現不一致」。**

這決定了一件事：**下面每一階段都必須包含「消滅接縫」的部分，不能只加功能。**
消滅接縫的手段這一輪也驗證過了 —— 合併成一個型別（`FacePlane`）、
換成 capability（`ISketchConsuming`）、換成工廠（`EditableValueRow`）。
共同點是：**讓不一致變成不可能，而不是再寫一個測試去抓它。**

---

## 第 0 階段：把地基上的裂縫補完 ✅ 已完成（M17.13）

在加任何功能之前。

- **接縫稽核**：把所有「A 建、B 讀、中間靠約定」的地方列出來，逐一改成單一型別／capability／工廠。
  已知的起點：feature 建立指令的訊息、序列化的 `FeatureData` ↔ `FeatureSnapshot`（兩份平行欄位清單）、
  屬性面板的每一種 row 建構。
- **草圖工具列**：36 個圖示已經拆成兩排，但這是止血。需要的是分組（繪圖／修改／約束／標註），
  或改成 Onshape 式的下拉群組。
- **`--selftest` 的樣本覆蓋**：這一輪發現 fillet 的檢查只在 `m8-chain` 樣本裡跑，
  平常的 `--selftest` 根本到不了。CI 應該跑**每一個**樣本，而不是預設那一個。

**為什麼先做**：接下來每一階段都會加接縫。地基有裂縫時往上蓋，只會讓裂縫更難找。

## 第 1 階段：拓樸命名 ✅ 已完成（M17.13–M17.14）

四項全數完成：`CreatedBy`、`FaceQuery`、草圖跟隨面、查詢組合。

**這是整個專案最大的單一缺口，而且它已經開工了。**

M17.12 建立的 `EdgeQuery` 是正確的架構：**存句子，每次重算重新回答**。
現在的詞彙只有三句（所有邊／某方向最外側的面／平行於某方向），
所以點凹槽底面會被拒絕，面草圖也還不能追蹤面。

要做的是把同一個機制擴到能講出真正需要的句子：

1. **`CreatedBy{featureId}`** —— 「Pad001 造出來的那些邊／那些面」。
   這是 Onshape 最常用的查詢，也是**唯一能撐過幾何移動**的一種，
   因為它描述的是**來歷**而不是位置。
   需要在建構時記錄 OCCT 的 modelling history（`BRepAlgoAPI` 的 `Modified`/`Generated`），
   並在每次重算時重新記錄。這是本階段的技術核心。
2. **面查詢**，和邊查詢共用同一套：`FaceQuery`。
3. **面草圖真正追蹤面** —— 目前是凍結平面（ADR-M17-028）。
   有了 `CreatedBy`，草圖可以存「Pad001 的頂面」，面移動時草圖跟著走。
4. **查詢的組合**：交集、差集（「Pad001 造的邊，但不含頂面的」）。

**這一階段解鎖**：真正的選邊圓角、面草圖跟著模型走、
之後每一個需要指名幾何的功能（拔模、薄殼、掃掠的路徑）。

**風險**：OCCT 的 history 在布林運算鏈上會斷。要有「查詢失效」的明確回報，
而不是靜靜地比對不到 —— 這一點 M17.12 已經立好規矩了。

## 第 3 階段：3D feature 補齊（2–3 個 milestone）

- **掃掠（Sweep）** 與 **放樣（Loft）** —— 需要第 2 階段的雲形線才真的有用
- **薄殼（Shell）** —— 需要第 1 階段的面查詢（挑要開口的面）
- **拔模（Draft）** —— 同上
- **孔特徵（Hole）** —— 直徑／深度／穿通／沉頭／埋頭，放在面上。
  目前只能用 Pocket 手動做
- **3D 陣列**：線性、環形、鏡射
- **多實體（multi-body）** 與布林：聯集、差集、交集

## 第 4 階段：組合件（3+ 個 milestone）

這是另一個檔案型別、另一套約束求解器（3D 的，6 自由度），
以及另一棵樹。不要低估。

- 零件實例、配合（Mate）約束、自由度顯示
- 干涉檢查
- 爆炸圖

**為什麼排這麼後面**：組合件會放大前面每一個缺口。
零件內部的拓樸命名不穩，配合就會在零件更新後失效 —— 而且更難診斷。

## 第 5 階段：工程圖（2–3 個 milestone）

- 視圖投影（前／上／右／等角、剖視、局部放大）
- 尺寸標註、公差、表面粗糙度、熔接符號
- 標題欄、零件表（BOM）
- 匯出 PDF / DXF

## 貫穿所有階段的三件事

**1. 匯入匯出**
STEP 匯入匯出應該早做（第 1 或第 2 階段），因為它是**唯一能讓 EP3D 和真實世界交換資料的通道**。
STL 匯出給 3D 列印同理。DXF 匯入已經有了。

**2. 效能**
目前每次重算都是全鏈重建。依賴圖已經知道誰髒了，
但 kernel 這一層沒有快取。零件大到一定程度就會卡。
**觸發點**：等到單次重算超過 1 秒再處理，不要提早最佳化。

**3. 使用者能看懂發生什麼事**
這一輪反覆出現的教訓是：**沈默的成功比失敗更糟**。
每加一個指令，同時回答三個問題 ——
它做了什麼？沒做的話為什麼？我現在該做什麼？
`--selftest` 是唯一會抓到「按鈕不存在」「訊息沒出現」的東西，繼續餵它。
