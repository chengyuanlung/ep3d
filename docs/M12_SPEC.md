## 4. M12.0 — Core：sketch 幾何與約束的 undo

**這是 UI 之外唯一動到 Core 的地方，而且是被迫的。**

M12 之前 `UndoDelta` 涵蓋 parameter / feature / frame / connector，**不涵蓋 sketch 內容**。
在只能用程式建 sketch 的年代看不出來；有了滑鼠工具，「畫一條線按 Ctrl+Z 沒反應」是第一個會踩到的缺陷。

新增：

```cpp
SketchEntityExistenceEdit      { sketchId, entityId, geometry, addedByTheEdit }
SketchConstraintExistenceEdit  { sketchId, constraintId, data, addedByTheEdit }
```

新增 facade：`PartDocument::addSketchEntity(sketchId, geometry)` —— 記錄 delta 的那條路徑。

三個規則：

1. **還原走 `restoreEntity` / `restoreConstraint`，不走 `add*`** —— entity 必須以**原本的 id**
   回來，否則 undo 會讓所有引用它的 constraint 變成孤兒（A03）。
2. **刪除 entity 時，被串聯刪掉的 constraint 各自記一筆，並排在 entity 那筆之前** ——
   delta 是反序 undo 的，entity 必須先回來，constraint 才有東西可附著。
3. **記錄的是 sketch 實際存下來的幾何**，不是傳入的參數。

### 4.1 已知缺口：建立 sketch 本身不可 undo

`UndoDelta` 沒有 sketch-existence 這一項。要補它得同時決定「undo 一個被 feature 引用的
sketch 時，那些 feature 怎麼辦」，那是 Core 的裁決，本 milestone 沒有做。

因此 **`New Sketch` 不可 undo**，且 `newSketchCommand()` 回傳的狀態列訊息會明講這件事。
Sketch 內畫的每一樣東西都可以 undo。

## 5. M12.1 — 畫布與工具

### 5.1 座標與視圖

- sketch (u,v) mm；**+v 向上、pixel +y 向下**，翻轉只存在 `CanvasView` 一處。
- zoom **有上下限**（`kMinPixelsPerMm` / `kMaxPixelsPerMm`）。無界縮放會讓 `toSketch()`
  回非有限值，而下一次點擊就把它寫進文件。
- `FitView` 對空 sketch 給 100 mm 預設視野，且**原點永遠在框內**。

### 5.2 吸附（§4.2）

優先序：`Endpoint` > `Origin` > `OnCurve` > `Grid` > `Free`。

兩條硬規則：

1. **`SnapResult::ref` 只會是 solver 認得的「點」**：Point 的 `Whole`、Line 的
   `StartPoint`/`EndPoint`、Circle/Arc 的 `CenterPoint`。
   **弧的兩個端點刻意不在其中**——solver 對弧只有圓心與半徑兩組變數，
   給它一個 ref 會讓推斷出來的 constraint 指到**半徑**。弧端點仍可用 `OnCurve` 吸到位置，但不產生 ref。
2. **Shift 抑制推斷**：回傳原始座標且**不回報 ref**，狀態列同時顯示抑制中（§4.2 第 3 點）。

### 5.3 推斷即 constraint 產生器（§4.2 第 1 點）

吸到既有點後建立的幾何，會**真的產生 `CoincidentConstraint`**，有 ConstraintId、計入 DOF、
在 constraint 清單中可見可刪。任何一條自動 constraint 被拒絕，**整個命令 abort**——
半套用的推斷會讓 DOF 說謊。

連續畫線的接點也是如此：下一段的起點透過 `afterApply()` 拿到**前一段的 EntityId**，
建立真正的 coincident。套用失敗時 `afterApply({})` 讓它退化成純幾何重合而**不捏造 ref**。

### 5.4 工具

| 工具 | 點數 | 產出 |
|---|---|---|
| Select | — | 選取（點擊 toggle，多選**不需修飾鍵**，§13.1） |
| Point | 1 | SketchPoint |
| Line | 2 | SketchLine，**連續**（Esc 結束） |
| Rectangle | 2 | **4 條 Line + 2 H + 2 V + 4 Coincident**（§4.1：矩形是線加約束，不是矩形型別） |
| Circle | 2 | 圓心 + 圓周點 |
| Arc | 3 | 圓心 + 起點 + 終點（逆時針掃掠） |

退化輸入（零長線、零半徑、零面積矩形）**丟掉那一次點擊並繼續等待**，而不是丟出一個
使用者無法解讀的失敗命令。

## 6. M12.2 — 約束與尺寸

### 6.1 約束以「選取」驅動，不是各自一個點擊序列

選 → 按命令。四種：Coincident（2 點）、Horizontal / Vertical（≥1 線）、Fix（≥1 點）。

**拒絕一定給理由**，且指名是哪個元素不合格（§8「不能只顯示 Solver failed」的同一條精神）。

以端點選中一條線後下 Horizontal，ref 會正規化成 `Whole` —— 否則使用者眼中的一條線會產生兩個約束。

### 6.2 尺寸：單一命令 + 選取推斷（§7.1）

| 選取 | 產生 |
|---|---|
| 1 條線 | Length |
| 1 個圓 | Diameter |
| 1 個弧 | Radius |
| 2 個點 | Distance |
| 2 條線 | Angle |

**這動用了 `todo.md` §16 第 3 項的 owner 裁決點**：現行 Core 是「型別各自一個命令」，
本 milestone 的 UI 採用**單一 Dimension 命令 + 推斷**，並額外提供 Radius / Diameter 兩個
顯式覆寫（圓/弧上唯一真正歧義的情況）。**此裁決尚待 owner 追認**，若否決，
改動範圍限於 `SketchCanvasModel::requestDimension` 與工具列上的一個按鈕。

其他規則：

- 尺寸建立時 Parameter **以量到的現值播種**，所以加尺寸不會移動任何東西。
- Parameter 自動命名 `d1`、`d2`…（長度）與 `a1`、`a2`…（角度），符合 M11.4 的名稱規則，
  因此可被 `#d1` 引用。
- **一個尺寸命令 = 建立 Parameter + 建立 constraint = 一步 undo**。
- 角度**內部 radian、介面 degree**，轉換只在 `CommitDimensionValue` 一處。
- 尺寸欄位接受**運算式**（M11）：`#Width / 2`。被拒絕時保留使用者輸入並附三行 caret 說明。
- 編輯器顯示的是**運算式原文**而非求值結果——顯示 40 會讓第一個按鍵毀掉公式。

### 6.3 Constraint manager（§6.3）

右側 dock，四欄：Constraint / On / Value / Status。

- 每列帶 ConstraintId、型別、參與元素、綁定的 Parameter 與值。
- **Status 欄是文字**（`OK` / `AT FAULT`），不是顏色（A06）。`AT FAULT` 來自
  `Sketch::offendingConstraints()`，這就是 §8.2「可定位」的落地。
- 雙擊尺寸列開啟編輯器；選單可刪除選定的 constraint。

### 6.4 狀態呈現（§8）

`DescribeSketchStatus` 對六種 solver 狀態各給一個 **badge + 句子**：

| 狀態 | badge | 句子要點 |
|---|---|---|
| Solved | `OK` | Fully constrained — DOF 0 |
| UnderConstrained | `DOF` | Under constrained — DOF *n* |
| OverConstrained | `REDUNDANT` | **多餘但相容**，與 conflicting 分開（§8.2 第 3 點） |
| Conflicting | `CONFLICT` | 互相矛盾 |
| InvalidInput | `INVALID` | 參考或值不可用 |
| NumericalFailure | `FAILED` | **收斂失敗，不是模型矛盾**（§8.2 第 4 點） |

從未求解過的 sketch **不得回報 DOF 0**——0 在本專案代表完全約束。

狀態列版面：`[badge] 句子   |   提示或上一則訊息`。
badge 與句子**永遠在**；命令訊息只佔提示的位置。第一版把訊息鋪滿整行，結果一下命令
約束狀態就消失，而那正是使用者最想知道它的時候。

## 7. M12.3 / M12.4 — Widget 與 Shell

- 中央區改為 `QStackedWidget{3D viewer, sketch canvas}`。**Sketch 是一個模式**（`todo.md` §14）。
- Sketch 工具列與 constraint dock **只在 sketch 模式出現**；所有 sketch 命令的
  enabled 狀態由模型決定，不會出現「可以按但什麼都不會發生」的按鈕。
- 顏色語意沿用 §8.1（藍=未完全約束、黑=完全約束、紅=有問題），但**每一項都有第二通道**：
  選取用線寬、約束用字母標記（H/V/o/X）、吸附用形狀（方=端點、圓=圓心、菱=原點、叉=在曲線上、點=格線）、
  狀態用文字 badge。
- 滑鼠：左鍵=工具/選取，中鍵拖曳=平移，滾輪=縮放，右鍵/Esc=取消。Shift=抑制推斷。

第三層是 M6.14 的教訓：前兩層問的都是模型，只有它問 widget「你到底畫了什麼」。
`SketchCanvasWidget` 因此在 `paintEvent` 內**記錄實際繪製的數量**，而不是事後重算。

這一層立刻抓到一個只有它看得到的缺陷：**sketch 模式下按 Ctrl+Z，畫布不會更新**。

畫布與 constraint 面板的存在，於是文件裡的幾何已經消失、畫面還在畫它。
修正是把這兩者納入 `refreshAll`；斷言留在 selftest 裡（undo 後 `paintedDimensions()` 必須為 0）。

## 10. ADR

- **ADR-M12-001** — 決策層 Qt-free。理由：owner 的 D1 裁決要求 2D 與 OCCT overlay 共用一套；
  加上 M6.14 的教訓，能被測試直接呼叫的東西應該最大化。
- **ADR-M12-002** — sketch 幾何與約束納入 undo（M12.0）。理由：滑鼠工具讓「Ctrl+Z 沒反應」
  從理論缺陷變成第一個會被踩到的缺陷。還原一律用 restore 路徑保住 id（A03）。
- **ADR-M12-003** — 吸附產生的 ref 只限 solver 有變數的點；弧端點不給 ref。
  理由：否則推斷出的 constraint 會指到半徑變數。
- **ADR-M12-004** — 矩形 = 4 線 + 8 約束，單一 transaction。理由：§4.1 明文。
  （ADR-M12-011/012 之後：8 條是**內部**約束。被點到的兩個角另外可能各自帶一條
  推斷約束（落在原點→Fix；落在現有點→Coincident），所以總數是 8、9 或 10。）
- **ADR-M12-005** — 尺寸採單一命令 + 選取推斷（§7.1），**待 owner 追認**（`todo.md` §16.3）。
- **ADR-M12-006** — 多選不需修飾鍵（§13.1），全域一致。
- **ADR-M12-007** — 狀態列的 badge 與句子永遠在，命令訊息只佔提示位置。
- **ADR-M12-008** — 建立 sketch 不可 undo，且在狀態列明講（§4.1）。
- **ADR-M12-009** — `refreshAll()` 必須同時重建 sketch 畫布與 constraint 面板。
  理由：任何「從文件重建 shell」的路徑（Undo/Redo/Recompute）都必須涵蓋它們，
  否則會出現文件已改、畫面未改的狀態。
- **ADR-M12-010** — sketch 的單字母快捷鍵使用 `Qt::WidgetWithChildrenShortcut` 並掛在畫布上。
  理由：window-scope 的單字母快捷鍵會在文字編輯器之前攔截按鍵——
  在尺寸欄位輸入 `#Width / 2` 會在 `h` 上觸發 Horizontal。

- **ADR-M12-011** — 繪圖時落在原點的點，自動產生 **Fix**（§4.2）。
  理由：原點是唯一「有吸附、卻沒有 element」的目標，Coincident 無法表達它——
  沒有 origin entity 可以當第二個參考。若只把游標吸過去而不產生約束，
  那就是 §4.2 明文禁止的繪圖期磁吸：使用者看到的是已定位的草圖，
  DOF 卻仍有兩個平移自由度。Fix 是 ADR-M5-005 用來消掉這兩個自由度的同一個機制。

  三條邊界，都是為了讓這條約束不說謊：

  1. **只有幾何真正擁有的點才有資格**。圓只有中心（rim 點是半徑，不是點）；
     弧只有中心——第二點決定半徑、第三點只貢獻角度，兩個端點都不保證在游標處。
     這與 ADR-M12-003 是同一條理由的兩個面向。
  2. **矩形只固定被點到的那兩個角**：第一次點擊是第 0 邊的起點，第二次是第 2 邊的起點。
     另外兩個角是推導出來的，使用者從未把游標放上去。
  3. **不會產生第二條 Fix**。SnapCursor 中已定義的點優先於原點，
     所以第二個畫在原點的東西會吸到第一個已被 Fix 的端點並得到 Coincident；
     line chain 帶過去的端點同理。多一條 Fix 就是 §8.2.3 要求必須與衝突區分開來的
     redundant，沒必要自己製造一個。

  抑制推斷（§4.2.3）連同 Fix 一起抑制：推斷出來的 Fix 也是推斷。

- **ADR-M12-012** — 矩形被點到的角落若吸附到既有點，產生 **Coincident**（§4.2）。
  理由：這條原本漏掉了——Line / Circle / Arc / Point 的吸附都會產生 coincidence，
  只有 Rectangle 沒有。缺這一條的後果不是「少一個便利功能」，而是
  **DOF 會說謊**：使用者看到矩形的角接在既有線的端點上，草圖卻仍把那 2 個自由度
  算成未用掉的；一旦任一邊被拖動或被 solver 移動，兩者就分開。
  這正是 §4.2 拒絕「繪圖期磁吸」的同一個理由。

  對應關係與 ADR-M12-011 相同：第一次點擊 = 第 0 邊起點，第二次 = 第 2 邊起點。
  兩個角可各自吸附，因此推斷出的 coincidence 是 0、1 或 2 條。

  **與 Fix 互斥**：SnapCursor 只有在附近沒有已定義點時才會走到原點分支，
  所以一個角落要嘛接到某個東西、要嘛被釘住，不會兩者皆是。
  抑制推斷同樣一併抑制（§4.2.3）。

- **ADR-M12-013** — Constraint 面板的「選取」是獨立的 highlight 通道，不動 canvas selection（§6.3、§8.2.2）。
  理由：§8.2.2 要求「點選 conflicting 的 constraint 時高亮對應幾何」，
  但若直接改寫 canvas 的 selection，就會把使用者原本選的東西洗掉——
  §13 對 dialog 欄位講的是同一條規則。因此 highlight 自成一個 channel：
  glyph 加一圈外框（**形狀**，不是換色，A06；換色會跟 AT FAULT 的紅撞在一起），
  被指涉的幾何加粗線寬但**不換色**（顏色已經被 §8.1 的求解狀態佔用）。

  **Highlight 必須跨 panel rebuild 存活，且以 id 記憶而非 row index。**
  每次 recompute 都會重建這些列，若 highlight 跟著消失，
  它就會剛好在使用者盯著草圖收斂的那一刻閃掉；用 row index 記則會在
  刪除或新增後指到別人身上。

- **ADR-M12-014** — 刪除 constraint 要有**面板上的按鈕**，不能只有選單項（§6.3）。
  理由：§6.3 描述的是「選一列、按垃圾桶」。原本只有
  `Constrain > Delete Selected Constraint`，功能存在但沒人找得到——
  而這正是 over-constrained 草圖**唯一的復原路徑**。
  按鈕的 enable 狀態跟著選取走：永遠可按、按了才說「請先選一列」的按鈕，
  是一個看起來可用而實際不可用的控制項。

- **ADR-M12-015** — Constraint badge 的**版面計算放在 Qt-free 層**（`ConstraintBadgesFor`）。
  理由：badge 變成**可點**之後，繪製與 hit-test 必須對同一份版面。
  原本兩者「剛好一樣」只因為都是那三行；一旦任一邊被改，
  症狀就是「badge 畫在這裡卻點不到」——而且沒有任何測試看得見。
  像素位移（+6/+6、slot × 15、19×14 的框）留在 widget：
  badge 是**用讀的**，所以在任何縮放下都保持同樣大小，理由與箭頭相同。

- **ADR-M12-016** — 在畫布上點 badge = 選取該 constraint；`Del` 刪除它（§6.3）。
  §6.3 的原文就是「在畫布上點選 constraint 圖示後按 Delete」。

  **點 badge 會清掉幾何選取**，這是 highlight 唯一會動到 selection 的地方，
  且與 ADR-M12-013 不衝突——那條講的是**面板**的列選取不得覆蓋畫布選取；
  這裡是畫布上的點擊，本來就會改變畫布選取。理由是 `Del` 必須只有一個意思：
  若還留著被選的邊，「刪除」就變成一個問句而不是一個命令。
  反過來，點在幾何或空白處會清掉 badge highlight，理由相同。

  **Del 有兩條入口，必須共用同一個決策**（`deleteSelectionOrHighlightedConstraint`）。
  這是實作時踩到的真實缺陷：shell 已經把 `Del` 綁在一個 scope 為
  `WidgetWithChildrenShortcut` 的 toolbar action 上，Qt 會讓 action 先取用，
  所以只寫在 `keyPressEvent` 裡的判斷**使用者永遠走不到**。
  是 smoke test 抓到的——單元測試看不到 Qt 的事件路由。

- **ADR-M12-017** — Sketch 原點是一個**真實的、被 Fix 的 Point entity**，
  由 New Sketch 自動建立；既有 sketch 可用工具列的「Origin Point」補上（owner 裁決，2026-08-20）。

  問題：畫布一直有畫原點記號、也一直吸附得到，但那只是一個**記號**——
  背後沒有 entity，所以選不到，也就無法「從原點標尺寸到某個角落」，
  而那是幾乎每張機械草圖的第一個尺寸。

  為什麼不做「solver 認得的常數點」：`DistanceConstraint` 的殘差吃 4 個變數，
  一個常數點需要新的殘差型別；而且 Coincident / Horizontal / Vertical …
  每一種可能指到原點的約束都要再來一次。
  一個**被 Fix 的普通 Point** 免費換到選取、標註、約束清單、序列化與 undo，
  而 solver 一個新詞都不用學。DOF 也不變：多 2 個變數、多 2 條約束。

  **與 ADR-M12-011 的互動（重要）**：原點一旦是真實的點，
  `SnapCursor` 的「已定義點優先」就會讓角落吸到**那個點**並得到 Coincident，
  而不是走 bare-origin 的 Fix 路徑。幾何結果相同，但更好——
  角落與原點從此是 solver 眼中的同一個東西。
  ADR-M12-011 的 Fix 路徑仍然有效，用於**沒有原點的 sketch**：
  DXF 匯入、程式建立、以及使用者自己刪掉原點之後。

  原點是**普通 entity**：會被列出、可刪除、undo 會還原它。沒有任何特例，這正是重點。

- **ADR-M17-001** — 水平／垂直距離是**兩個獨立的 constraint 型別**，且**帶正負號**（§7.1）。
  §7.1 明列「兩點 → 直線距離**或水平／垂直距離**」，EP3D 原本只有前者。

  **為什麼帶正負號**：殘差是 `(b.u - a.u) - target` 而不是 `|b.u - a.u| - target`。
  絕對值在 0 處沒有導數，而那正是「兩點目前垂直對齊、卻要指定水平距離」時
  solver 所在的位置。有號形式處處平滑，Jacobian 那一列是常數 `(-1, +1)`。
  代價是 target 的**正負有意義**：UI 在建立時把 a、b 排序讓值為正，
  之後輸入負值 = b 換到 a 的另一側——這是明確可解釋的行為，
  而不是被拒絕、或悄悄解成鏡像。

  **為什麼是兩個型別而不是 Distance 加一個軸向旗標**：與整個 variant 的理由相同——
  每個型別只帶它需要的東西，漏掉其中一個的 caller 會編譯失敗而不是執行期出錯。
  這次確實發生了：加型別後 serializer 的 `static_assert` 立刻指出未處理的分支。

  **不從選取推斷**：兩個點可以是三種量測，替使用者猜就是 §26 禁止的 silent guess。
  兩者各有自己的命令與圖示。

  Schema 升到 **v13**；`a`／`b` 的順序照寫不正規化，因為順序就是語意的一部分。

- **ADR-M17-002** — `Esc` 一次就回到箭頭（Select）。
  原本要按兩次：第一次丟掉半成品、留在工具裡，第二次才回到 Select。
  理由是「放棄一條線的人大概想再畫一條」——但實務上 Esc 就是「停」，
  按一次之後接著點選東西的使用者會多畫出一條不要的線。
  再畫一條只要點一下工具鈕；清掉不小心產生的幾何則不然。
  連續線的 chain 存在 `pending_` 裡，同一次按鍵一起清掉，行為不變。

  **工具列的 checked 狀態必須跟著走。** 原本只在按鈕自己的 handler 裡設定，
  於是 Esc 讓畫布回到箭頭、工具列卻還顯示 Rectangle 被按下——
  model 對、畫面錯，正是本專案一再要抓的那一類缺陷。
  現在由 `syncSketchToolButtons()` **從畫布讀回**，並掛在 `presentationChanged` 上；
  Esc 的處理也集中在 `SketchCanvasWidget::pressEscape()`，
  理由與 Delete 相同：決策必須能被 Qt 事件以外的東西呼叫，否則只有帶焦點的視窗測得到。

- **ADR-M17-003** — 選取的 entity 會畫出**端點控制點**，點它會**收窄**選取而不是加選。
  端點一直都選得到，但使用者沒有辦法知道、也沒有目標可瞄。

  **收窄而非加選**是這條規則能用的關鍵：若點端點是「加選」，
  選取就會是「一條線 + 一個點」，而 §7.1 沒有這種組合的尺寸，命令會被拒絕——
  控制點想支援的流程反而走不通。第二次點擊是對第一次的**細化**
  （「那條線的**這一端**」），不是第二個要量測的東西。
  這不違反 §13.1 的「多選不需修飾鍵」：整體與它自己的端點從來不是兩個獨立的 pick，
  點**別的** entity 的端點仍然是加選。

  控制點只畫 solver 有變數的點（ADR-M12-003）：線的兩端、圓／弧的圓心、點自己。
  弧的兩個端點不畫——那裡的參考會解析到半徑變數。

- **ADR-M17-004** — Undo／Redo 上主工具列，並帶圖示。
  原本只有選單項與 Ctrl+Z／Ctrl+Y。快捷鍵不是問題，
  問題是「現在有沒有東西可以復原」這件事只能靠打開選單才看得到；
  一個變灰的按鈕一眼就回答了。動作物件與 Edit 選單共用，
  所以 enable 狀態仍然只在 `refreshCommandStates` 一處決定。
  主工具列採 icon + 文字（不是純圖示）：它只有五個使用者早就熟悉名字的命令，
  拿掉文字省下的空間沒有人需要。

## 11. M17 — AutoCAD 2D 工具集移植（owner 裁決，2026-08-20）

Owner 要求把 `D:\Program2\easycad\EasyCad`（VB.NET，AutoCAD R12 風格）的 2D 繪圖功能
帶進 sketch：polyline、offset、trim、fillet …，依相依順序逐步進行。

**根本差異，也是本節唯一重要的一句話**：
EasyCad 畫的是**幾何**，EP3D 的 sketch 畫的是**幾何 + 約束**。
§4.1.1 已明文：sketch 內的 Fillet / Chamfer / Trim / Extend / Offset / Mirror
都是「產生 entity + constraint 的複合操作」。
只搬演算法而不產生約束，等於讓 DOF 說謊——正是 §4.2 反對繪圖期磁吸的同一件事。
程式碼無法共用（VB.NET → C++），可移植的是**演算法與命令語意**。

排程（相依順序）：

```text
1. 建構幾何 flag        ✅ ADR-M17-005
2. Polyline（close / undo）
3. Fillet / Chamfer / Offset      ← 由既有的 Tangent/Parallel/Concentric + 尺寸組成
4. 交點運算（line-circle、circle-circle）
5. Trim / Extend                  ← 需先裁決「被裁掉那段上的約束怎麼辦」
6. Symmetric constraint（§6.1「次階段」尚未實作）
7. Mirror
```

**不納入本輪**：Ellipse、Spline（新 entity 型別 + 新 solver 變數，各自是一個 milestone）；
Hatch、Block、Layer、Array（屬 §24 Drawing 的範疇，不是 sketch 幾何）。

- **ADR-M17-005** — 建構幾何是 `SketchEntity` 上的一個 **flag**（§4.1.1 第 2 點），schema v14。
  建構幾何照樣被畫、被吸附、被約束、被標尺寸，**只是不提供 profile 的邊**。
  平行的型別階層會讓 solver、serializer、canvas 的每個 switch 都變兩倍，
  只為表達一個布林值——而每一個 switch 都是兩半失去同步的地方。

  序列化**只在 true 時寫出**：沒有建構幾何的 sketch 與 v13 寫出的位元組完全相同，
  「欄位不存在」與 `false` 是同一件事，不留第三種狀態讓兩邊各自解讀。
  型別錯誤仍然**拒絕載入**——把字串當成 false 會讓損毀的檔案變成一個「安靜地不一樣」的模型。

  切換是**整個選取一步 undo**，且**每個 entity 一筆 delta**：
  混合選取（有些本來就是建構幾何）undo 後必須各自回到原狀，
  一筆「這五個變成建構幾何」的 delta 表達不了這件事。
  切換會 dirty 該 sketch——沒有座標移動，但 profile 看到的邊不同了。

- **ADR-M17-006** — 推斷出的 constraint 若其**既有**目標已不存在，**丟棄而不是讓整筆編輯失敗**。
  這是真實會發生的情況：在連續線中途按 Ctrl+Z 會刪掉 chain 正握著的那一段，
  而下一次點擊仍帶著它的參考。讓整筆失敗會使**使用者完全畫不下去**，
  還會收到一則關於他從未要求過的約束的錯誤訊息。
  誠實的結果就是 `afterApply` 在沒有 id 可掛時已經採取的那一個：畫出幾何、不發明參考。

  這**不是** §4.2 那個「丟掉使用者看見的吸附」的情況——被吸附的東西已經不在了，
  沒有關係可記錄，兩種做法的 DOF 相同。

- **ADR-M17-007** — 新增 `PointLineDistanceConstraint`：點到直線的**垂直距離**（§7.1）。
  它是 `PointOnObjectConstraint` 的尺寸孿生：**同一條殘差公式**，只是目標從 0 換成參數值。
  同一條公式是重點——兩者對「哪一側是正」永遠不會有不同意見。
  對的是**無限長直線**而非線段：線段外的點仍有明確的垂直距離，
  而「夾到最近端點」是另一個量，且在兩端各有一個轉折。

- **ADR-M17-008** — Offset 產生的是**關係**，不是複本（§4.1.1）。

  ```text
  line          Parallel(new, src) + Equal(new, src) + PointLineDistance(new.start → src)
  circle / arc  Concentric(new, src) + Radius(new)
  ```

  AutoCAD 的 OFFSET 複製完就走人；sketch 裡這樣做，複本會在下一次求解時漂走，
  而 DOF 會把使用者以為已經用掉的自由度算成還在。
  讓它成為 offset 而不是「剛好平行的第二條線」的，就是這些約束。

  直線的情況**刻意留一個自由度**：複本仍可沿自身方向滑動。
  要釘死它得再加第四條「兩端對齊」的約束，而使用者並沒有這樣主張過——
  offset 講的是垂直間距，誠實說出這件事比偷偷發明一個對齊要好。

  **參數以殘差公式量測後的值播種，不是以使用者要求的距離。**
  `(pu*dv - pv*du)/len` 在 start→end 的**右側**為正，所以放在左側的複本量到的是負值；
  若用要求的 +10 播種，參數就會和它自己的幾何互相矛盾，
  第一次求解就把複本翻到線的另一側。這是實作時真的踩到的。

- **ADR-M17-009**（修正既有缺陷）— **帶號的尺寸可以是負的，也可以是零**。
  `DimensionValueValid` 原本對「非角度」一律要求 `>= kMinSketchDimensionMm`，
  於是 `HorizontalDistanceConstraint` 文件裡寫的「輸入負值會把 b 移到另一側」
  **根本無法發生**——使用者一輸入負值，該約束就以 InvalidInput 被拒絕。

  ADR-M5-002 的規則（長度、半徑、點到點距離必須為正）針對的是
  **在零或以下就沒有意義**的量：零長度的線沒有方向、零半徑的圓是一個點。
  帶號的**分離量**不同：水平分離為零表示兩點垂直對齊，負值表示在哪一側；
  點落在線上時到該線的距離就是零。
  Horizontal / Vertical / PointLineDistance 三者現在與角度同列，接受任何有限值。

  教訓照舊：**文件寫了、但沒有測試走過的行為，等於不存在。**

`SketchSolveSession` 明文只把**圓心與半徑**當作弧的變數，
**角度範圍固定不動**；ADR-M12-003 也因此不讓弧的端點被參考。
可是 fillet 的整個意義就是那段弧的兩端要一直貼在兩條線上。
沒有弧端點變數的 fillet，會在第一次求解後與兩條線分家——
「看起來對，直到有東西移動」正是本專案一再在抓的那一類缺陷。
把弧端點納入求解會讓**每一張既有的弧草圖多出 2 個自由度**
（那正是 M5 當初留下該註解的理由），因此它是一個獨立的 milestone，不是一個命令。

- **ADR-M17-010** — 新增「就地修改 entity 幾何」的基礎設施：
  `SketchEntityGeometryEdit` undo delta + `PartDocument::setSketchEntityGeometry`。

  EP3D 原本**沒有任何**修改既有幾何的交易式路徑：幾何只有兩個來源——建立時、以及求解後的 commit。
  Trim、Extend、Chamfer 三者都必須把既有線段的端點往回移，全部卡在這一點上。

  **entity 保留原本的 id，這正是整件事的重點。**
  另一條路（刪掉再重建）會發出新的 id，並依 ADR-M5-009 連帶刪除它身上所有約束——
  於是被 trim 過的線回來時什麼都沒接著，而使用者只會看到「它不再是水平的了」。
  delta 兩端各存一份完整幾何而不是差分：形狀是 variant，
  「起點移動了」描述不了「圓變成弧」。

- **ADR-M17-011** — Trim v1：**只能 trim 線**，且**保留線上的約束**。

  **保留約束**（owner 於 2026-08-20 指示逕行實作，此處記錄所採裁決）：
  被移動的端點身分不變，所以指向它的每一條約束仍然成立——
  只是現在它說「鄰居要跟著到新位置」。丟掉約束等於默默丟掉使用者說過的話（§26）。
  若保留後幾何上做不到，solver 會報 conflicting——看得見，而不是無聲無息。

  **只有線可以當 target**：trim 弧會改變它的 sweep，而 `SketchSolveSession` 明文
  只把圓心與半徑當弧的變數（ADR-M12-003），
  被 trim 過的曲線會由「什麼都沒有」固定住。拒絕並說明理由，而不是做一半。

  **中段不做**：拿掉中間一段會把一條線變成兩條，
  「哪一半保留約束」是另一個問題，不靠猜。拒絕時把這個理由講出來。

  **Cutter 是「其他全部」**：指定 cutter 需要第二個挑選模式，目前沒有；
  「全部」正是 AutoCAD 在 cutter 提示按 ENTER 的行為。
  只在**兩者都真的相交**之處切：弧所在的圓延伸得更遠，
  在那裡下刀會切在一個畫面上什麼都沒有的位置。

- **ADR-M17-012**（兩個 UI 缺陷，都由 owner 發現）—
  1. **Offset 與 Distance to Line 曾經只有決策層與測試，沒有按鈕。**
     單元測試全綠，而命令對使用者而言並不存在——M6.14 最純粹的形態，
     而且是在我一邊寫著「要避免這件事」的時候發生的。
     現在 `--selftest --sample m12-sketch` 會**以使用者的方式**驅動這兩個命令。
     規則：**新命令未經 shell smoke test 走過，就不算做完。**
  2. **Trim 是一個 mode，而 mode 必須有出口。**
     選任何繪圖工具都會離開 trim 模式（`setTool` 清掉 `trimming_`）；
     否則 trim 會吃掉每一次點擊，於是每個繪圖工具看起來都壞了——
     按鈕亮著、游標變了、卻永遠畫不出東西。Esc 同樣離開。
     另外 `syncSketchToolButtons()` 必須**跳過** Trim 按鈕：
     它是 checkable 但不帶 tool data，那個迴圈會把它讀成「不是目前的工具」，
     在它剛被按下的瞬間又關掉。

- **ADR-M17-013** — Extend 與 Trim 共用同一套機制，並共用同一條「指著你要的東西」規則。
  拿 `TrimPlan` 回報，因為答案的形狀相同：**這條線、重塑後、一端移動**。
  端點由**點擊位置的近端**決定，不是另立一條使用者得記的規則。

  **只往前長，不往後縮**：位於該端**後方**的交點不算。
  Extend 是「長長」，一個線段已經穿過的邊界不是可以長過去的地方；
  往回伸去碰它會把線縮短，卻自稱 extend。
  停在**最近**的邊界：越過第一個擋住的東西，會穿過使用者看得出它應該停下來的幾何。

  Trim 與 Extend 是**互斥的模式**：一次點擊只能有一個意思，
  同時開著的畫布就得無聲地替使用者選一個。

- **ADR-M17-014** — Chamfer **刪掉轉角自己的 Coincident**，並補上兩條新的。

  這是整個命令裡真正屬於參數式的部分。原本那條約束說「這兩個端點是同一點」，
  而 chamfer 做的事就是讓它不再成立；留著它等於交給使用者一個**他沒有製造的衝突**。
  兩條新的 Coincident 把 chamfer 線的兩端接到兩個退縮點上，三段仍然是一條連續的走線。

  對草圖的淨效果是 **+2 個自由度**，而那兩個就是兩段退縮量。
  標上尺寸，轉角就被釘住；不標，chamfer 可以滑動——
  那是對「使用者到目前為止真正說了什麼」的誠實回報。

  **整個命令是一筆交易**：一次 delete、兩次幾何重塑、一次 add、兩次 add constraint，
  但只有**一次 Ctrl+Z**，因為那是使用者做的一件事。
  任何一步失敗就整筆回滾——做到一半的 chamfer 會鬆開轉角卻沒放上任何東西，
  比命令沒有執行更糟。

  **兩條不相接的線沒有轉角**：跨過空隙的 chamfer 會在使用者從未接起來的兩個東西之間
  發明幾何。以 `kProfileConnectivityToleranceMm` 判定，與 profile 用的是同一個容差。

- **ADR-M17-015** — `SymmetricConstraint`（§6.1「次階段」最後一項），schema v16。
  **兩個點**對一條**線** 對稱；非尺寸型，不綁 Parameter。

  **兩條殘差，不是一條**——「互為鏡像」是兩件獨立的事實：

  ```text
  SymmetricAcross   兩者到該線的帶號距離「相加為零」：同樣遠、在相反側
  SymmetricAlong    兩者的連線與該線「垂直」
  ```

  少了第二條，兩個離線等距、卻沿著線各自滑開的點會完美滿足第一條，
  而它們根本不是鏡像。兩條殘差都以 mm 為單位，與其他位置類殘差共用同一個容差。

  **取兩個點而不是兩個 entity**：鏡射一條線的意思是它的**兩端**各自與複本的對應端對稱，
  用一對點約束來說既簡單又更通用——它同時能表達圓心、單獨的點、
  以及「只想固定一端、另一端保持自由」的線。
  整體形式會是同一個想法的第二種拼法（ConcentricConstraint 記過這個理由）。

  **鏡射軸是一個線 entity，不是存下來的軸**：移動那條線，所有對它鏡射的東西都跟著動。
  存一份軸的複本，等於存了一個「從此刻起就開始與該線不一致」的東西。

- **ADR-M17-016** — Mirror 產生的是**被綁住的複本**，不是圖章。
  複本的每一個點都以 Symmetric 綁回原件，所以移動來源、或移動鏡射線本身，
  反射都會跟著走。只複製的鏡射會在下一次求解時漂走，
  而 DOF 會把使用者以為對稱性已經用掉的自由度算成還在。

  - **線：兩端都綁**。只綁一端會讓複本繞著另一端擺動——那只是外觀上的鏡射。
  - **圓：Symmetric（圓心）+ Equal（半徑）**。
    對稱決定圓心的位置；沒有 Equal，複本可以被單獨改大小卻仍然「對稱」。
  - **弧：拒絕**，理由與 fillet 同源——弧的 sweep 不是 solver 變數（ADR-M12-003），
    複本的圓心與半徑會被綁住，兩個端點卻各走各的。

  **鏡射軸是選取中的最後一條線**：這是使用者自然的操作順序（先選東西、再選軸），
  不需要額外的挑選模式。若最後選的不是線，明白告訴他，
  而不是把他最後選的那個圓拿來當軸。

  整個命令是**一筆交易、一次 Ctrl+Z**，不論鏡射了幾個。

- **ADR-M17-017** — 拖曳幾何：**先釘、不行再種**（two attempts），
  且問題必須在**任何東西移動之前**建立。

  拖曳是同一個問題被重複問：「把這個點放到游標，其餘重新求解」。
  游標的釘住是**附加到問題上的兩條殘差**，不是加進文件的約束——
  真的加一條 Fix 會在每次滑鼠移動時建立又刪除、會進 undo stack、
  而且在按著滑鼠的期間會出現在約束清單裡。

  **兩次嘗試，兩次都必要**，各自漏掉一整類拖曳，而且每一類都花了兩個失敗的測試才發現：

  ```text
  1. 釘住   被拖的點以硬殘差「釘」在游標上。
            這是拖轉角能動的原因——coincident 的鄰居會被精準拉到游標。
            只用「種初值」的話，solver 可以靠移動「兩個」點來滿足 coincidence，
            而 minimum-norm step 正是這麼做：轉角只走到游標的一半，手感全毀。

  2. 只種初值 與模型矛盾的釘住「就是」矛盾，solver 正確地回報 Conflicting——
            於是被標了長度的線一旦拖過自己的長度，就「完全不動」。
            拿掉釘住之後問的是比較弱、但正確的問題：
            「從這附近出發，然後合法」——於是會滑、會擺、會彈回去，正如預期。
  ```

  先釘住，因為那是比較強的承諾：模型允許時就精準遵從游標，不允許時盡量靠近。

  **順序是會壓垮一切的細節**：`FixConstraint` 的目標值是**建立問題時**從幾何讀出來的
  ——它的意思是「這個點現在在哪」。
  先把游標寫進 sketch、再建立問題，等於把草圖裡**每一條 Fix 都重新基準化到游標上**，
  於是被釘死的點可以跟著滑鼠跑到任何地方，還一路回報 Solved。
  這個版本上線了大約十分鐘，被 `M17_DRAG_002` 抓住。
  現在游標只作為 **initial guess** 套用，草圖的幾何在求解收斂前完全不動。

  **預覽不記錄、不 dirty**（與 ADR-M16 的尺寸拖曳同理）：
  橫跨畫布的一次拖曳是**一個**動作，一千步 undo 是沒有人走得回去的歷史。
  `commitSketchDrag` 在放開時記錄**每一個移動過的 entity**——
  不只是被抓住的那個，因為受約束的拖曳會帶動鄰居，
  只還原被抓住那一點的 undo 會把草圖留在使用者從未看過的狀態。

  **沒動就不記錄**：按一下再放開不會產生 undo 步驟，這也是「按下同時選取並抓起」
  之所以可行的原因。**Esc 中途放棄**會整份還原，同樣不留任何痕跡。

  **回傳 solver 的裁決，不是 bool**：「它沒有動」不是使用者能據以行動的答案（§8）。

- **ADR-M17-018** — 弧的兩個端點成為 solver 變數（取代 ADR-M12-003 的禁令）。

  M5 把弧的角度範圍「固定不動」，理由是當時沒有任何約束能驅動弧的端點，
  放開角度只會多出沒人能消掉的自由度。M17 讓這兩個理由都不再成立：
  fillet 的全部意義就是那段弧的兩端要一直待在兩條線上，而 Coincident 正能держ住它們。

  順帶修正一個**一直存在的錯誤**：一段自由的弧有五個獨立的量
  （圓心 2、半徑 1、兩個角度 2），EP3D 卻一直回報 3 個自由度——**少算了兩個**。

  **做法是把端點變成真正的變數**，再用每個分量一條殘差把它綁回圓心／半徑／角度：

  ```text
  ArcTipU   tip.u - (centre.u + r cos(angle))
  ArcTipV   tip.v - (centre.v + r sin(angle))
  ```

  一個端點 = 兩個變數 + 兩條方程式 = **不增加任何自由度**，
  而**每一個已經會固定「點」的約束，都能固定弧的端點，而且不需要知道弧的存在**。
  另一條路是為 Coincident、Distance、Fix、PointLineDistance、Symmetric
  以及之後每一種約束各做一個「認得弧端點」的變體。這條路是四個 slot 與一個想法。

  **端點是導出的，不寫回**：角度才是狀態，端點是 ArcTipU/V 由它導出的結果。
  把解出的端點座標也寫回去，等於把同一件事存兩份，而那兩份可以開始互相矛盾。

  commit 路徑改為**先依 sub-element 分流、再依 entity 型別解讀**：
  線的 StartPoint 與弧的 StartPoint 都是「StartPoint 上的 U/V」，意思卻完全不同，
  合在同一組欄位裡會讓弧的端點覆蓋掉它的圓心。

- **ADR-M17-019** — Fillet：**弧 + 2×Coincident + 2×Tangent + 兩條線退縮**，一筆交易。

  等待 ADR-M17-018 的原因就在這裡。fillet 的弧不是丟在轉角裝飾用的——
  它的兩端必須**一直**在兩條線上，並且**一直**與兩者相切，穿過之後每一次求解。
  少了 Tangent，轉角今天是圓滑的、改一次參數之後就有折角；
  少了 Coincident，那段弧只是躺在缺口裡的一個裝飾。

  幾何：退縮量 = `r / tan(θ/2)`，圓心在角平分線上距轉角 `r / sin(θ/2)`。
  共線或反向的兩條線被拒絕——內切圓的切線長一邊是無限、另一邊沒有定義。
  半徑太大以致吃過線端也被拒絕，並說出是哪一種情況。

  與 Chamfer 共用 `FindCorner` 與「刪掉轉角自己的 Coincident」的規則：
  兩個命令問的是同一個問題，必須得到同一個答案。

  **測試的教訓**：第一版的 `M17_FIL_101` 只是 recompute 一次就檢查相切——
  而 fillet 建立時本來就是一致的，solver 無事可做，
  所以**即使把弧端點的綁定殘差整個拿掉，測試照樣通過**（mutation 存活）。
  現在它會先拖動其中一條線的遠端，強迫整個轉角重新求解——
  那正是「沒綁住的端點」會散開的時刻。
  **不會移動任何東西的測試，證明不了任何會在移動時壞掉的事。**

- **ADR-M17-020** — Mirror 與 Trim 開放給弧（ADR-M17-018 之後才可能）。

  **Mirror 一段弧**：反射會**反轉走向**。角度 θ 對方向為 φ 的線鏡射得到 `2φ - θ`，
  而逆時針走它的鏡像是從「反射後的終點」走到「反射後的起點」——所以兩者要對調。
  不對調就會畫出**互補的那一段弧**：同一個圓，使用者沒有鏡射的那一半。

  綁法是**交叉的兩個端點 + Equal，而「不是」圓心**：
  複本有五個自由度（圓心 2、半徑 1、角度 2）；
  兩條端點對稱是四條方程式，Equal 是第五條——**剛好定死**。
  再加上圓心對稱就是為已經用掉的自由度再列兩條式子：相容，
  但 solver 會理所當然地說每一個鏡射弧都 over-constrained，
  而 §8.2 希望那個回報是有意義的。

  **Trim 一段弧 = 移動一個角度**。端點就在角度所指之處（ADR-M17-018），
  所以這和移動線段端點是同一種編輯，只是用弧自己的狀態表達。
  切點以「沿掃掠方向的比例 [0,1]」表示，與線共用同一套詞彙，
  於是「使用者點到哪一段」的邏輯完全不必區分線與弧。

  新增 `CircleCircleCrossings`：兩圓交點。同心的情況**排除**——
  半徑相同的同心圓處處相等，而「處處」不是一組切點，
  那是一個使用者該看見的建模錯誤，不是一次默默挑一個地方下刀的 trim。

  **圓仍然不能被 trim**：切一個圓不是把它變短，而是把它變成一段弧——
  那是**種類**的改變，而每一條指名該圓 Whole 的約束會突然指向另一種東西。

  **測試的教訓（第二次）**：
  「鏡射弧」的第一版測試只檢查兩個端點落在反射後的位置——
  而不論角度有沒有對調，端點都是同樣那兩個點，
  於是「不對調」的 mutation 存活了。差別在**掃掠角**，現在測的是它。
  同樣地，shell 測試原本只要求 trim「有回話」，
  而拒絕訊息也是一句話——把弧從 hit-test 拿掉的 mutation 因此溜過去，
  在好幾個區塊之後才以無關的訊息失敗。現在它要求訊息含 "Trimmed"。

- **ADR-M17-021** — Revolve 上選單（Core 自 M8 就有，shell 一直沒有命令）。
  軸的選法：**唯一一條建構線就是軸**，不多問——那是製圖上的中心線慣例，
  而 ADR-M17-005 的 flag 正好讓它可被判定。
  **恰好一條**才算明顯：兩條建構線不是一個明顯的答案，取第一條是「披著慣例外衣的猜測」。
  其餘情況列出草圖裡的線讓使用者選——輪廓繞著**自己的一條邊**旋轉（矩形繞側邊 = 圓柱）
  是合法且常見的，不能因為沒有建構線就做不到。
  角度以**度**輸入、以弧度儲存（§7），並在狀態列講明面板顯示的是弧度。

- **ADR-M17-022**（缺陷，由 owner 發現）— **建立 feature 的命令必須回報它真正的結果。**
  `insertPadFromSelection` 無論如何都印出 "Pad created"。
  於是「矩形裡面畫一個圓」——profile 驗證器明確拒絕的兩個迴圈——
  回報成功，畫面上卻什麼也沒多出來：使用者被告知了與事實相反的事。
  現在三個命令（Pad / Pocket / Revolve）都以該 feature **自己的**診斷回報，
  依 id 從 recompute report 取出——文件層級的「有東西失敗了」會害使用者在樹裡翻找是哪一個。

  **仍未支援：帶內孔的 profile。** `ValidatedProfile` 只有一個外迴圈；
  矩形加內圓是兩個閉迴圈，會被拒絕。這是功能缺口，不是缺陷——
  但在修正之前，它至少會**說**自己做不到。

- **ADR-M17-023** — File > Open / Save / Save As。
  Open 只可能靠**重新指向**：`PartDocument` 刻意不可複製也不可移動，
  所以開檔不能「換掉一份文件的內容」，只能換掉「大家在看哪一份文件」。
  能做到是因為 MainWindow、DocumentPresenter、SketchCanvasWidget 內部一直都存**指標**。

  視窗**擁有**它載入的文件（`ownedDocument_`），但**不擁有**建構時傳進來的那一份——
  後者屬於它的擁有者，永遠不由這裡釋放。
  kernel 與 solver 是**應用程式的**、不是檔案的（ADR-M3-003／ADR-M5-003），
  載入的文件兩者皆無，因此從被取代的那份文件接手過來。
  載入失敗**什麼都不動**：loader 從不回傳半載入的文件。

  **測試的教訓（第三次）**：round-trip 測試原本存檔後直接開檔——
  那是拿一份文件跟它自己比，於是「視窗沒有重新指向」的 mutation 照樣通過。
  現在會在**存檔之後**替原文件加一個參數，讓檔案與記憶體中的文件不同，
  再確認視窗看到的是**檔案**那一份。

- **ADR-M17-024** — Profile 支援**內迴圈（孔）**（M4 起就標記為 deferred）。
  由 owner 的回報帶出來：矩形裡畫一個圓、pad 之後只得到一塊實心矩形。

  **一個症狀，兩個缺陷**：驗證器直接拒絕第二個迴圈，
  而命令無論如何都印出 "Pad created"（見 ADR-M17-022）。

  **判定規則是「包含」，不是大小、也不是繪製順序**：
  必須**恰好有一個**迴圈包含其餘所有迴圈，那個就是外邊界。其餘全部是孔。
  以下一律拒絕，而不是猜：

  ```text
  並列的兩個迴圈      → 那是兩個實體，不是一個帶孔的實體
  孔裡面還有一個迴圈   → 島（第二塊實體區域），當成單純的孔會把它悄悄弄丟
  互相穿越的兩個迴圈   → 一半在裡一半在外，既不是孔也不是邊界
  ```

  包含判定用的是**粗略的多邊形取樣**，而且只用來判定包含——
  近到答案取決於弦誤差的兩個迴圈，OCCT 本來也會拒絕。
  送進 kernel 的仍然是**精確曲線**。
  判定會檢查內迴圈的**每一個**頂點：單一取樣分不出「被包含」與「只是起點在裡面」，
  而「大致在裡面」不是一個 profile 可以是的狀態。

  **kernel 側**：`PlanarProfileDefinition` 多一個 `innerLoops`，
  每個內 wire 以**反向**加入 face——OCCT 以邊界方向分辨實體與空洞，
  與外圈同向的內 wire 描述的是第二個外邊界，
  結果是一個 OCCT 接受、而沒有人想要的實體。

  **測試的教訓（第四次）**：拿掉「反向」這一行的 mutation 存活了——
  因為當時所有檢查止於「這個實體是有效的」。
  方向錯誤的 face 照樣建得起來、照樣拉伸得出來、看起來也還是一塊板子，
  只是該有孔的地方是實心的。
  現在測的是**體積**（以及偏心孔的質心），那才是能分辨的東西。

- **ADR-M17-025**（缺陷，由 owner 以真實檔案回報）—
  **每一次選取變更都要重新評估命令的啟用狀態。**

  症狀：開啟一個「內容只有一張 sketch」的檔案之後，
  不管怎麼點那張 sketch，`Edit Selected Sketch` 都是灰的。

  原因**不在開檔**。`selectObject()` 會更新樹、3D 檢視與屬性面板，
  卻從不呼叫 `refreshCommandStates()`——
  於是啟用狀態只有在「剛好有別的命令去刷新它」時才會跟上。
  `finishSketchCommand()` 會刷新，所以平常「畫完 → 關閉 sketch → 再編輯」那條路一直是對的；
  而一份**只有 sketch** 的文件沒有別條路，缺陷才顯露出來。

  修正就是在 `selectObject()` 結尾呼叫一次——那是**所有**選取變更的唯一必經之處。

  這也解釋了先前那個「重新開檔後不能編輯 sketch」的回報：
  我當時用 `selectObject()` 直接驅動測試、繞過了選單，
  所以測試看不到它——**測試走了一條使用者走不到的路**。
  新的檢查改問 QAction 自己是否 enabled。

- **ADR-M17-026** — 新增 **Model 工具列**：Pad、Pocket、Revolve、Fillet、Chamfer。
  這些命令原本只存在於 Insert 選單裡，而**使用者得去選單裡翻找的命令，等於不知道它存在**——
  Revolve 就這樣被忽略了整整一個 milestone。

  工具列用的是**選單持有的同一批 QAction**，
  所以啟用狀態仍然只在 `refreshCommandStates()` 一處決定，
  兩個介面不可能對「這個命令現在能不能用」有不同意見。
  按鈕上用 `iconText()` 顯示短名（Pad / Pocket / …），
  選單保留描述性的長名（"Pad from Selected Sketch"）——有空間的地方才寫得下句子。

  三個新圖示刻意講同一句話的三種時態：**這是一個輪廓，然後它發生了什麼**。
  輪廓在三者中畫法完全相同，只有動作記號不同——那才是使用者真正要分辨的部分。
  Pocket 的箭頭是 Pad 的反向，因為兩個命令本來就是相反的。

  **沒有獨立的 Hole feature**，Core 也沒有。
  孔有兩條路：畫一個圓然後 Pocket，或（自 ADR-M17-024 起）
  直接把圓畫在輪廓裡面當內迴圈。Pocket 的 tooltip 明講了這件事，
  免得使用者去找一個不存在的按鈕。

- **ADR-M17-027**（缺陷，由 owner 回報：「pad，我改了 length 屬性，3D 物件的高度沒有變」）—
  **屬性面板上每一個可編輯的列，都必須帶著一個真的能寫入的 `field`。**

  `PropertyRow` 有八個欄位，最後一個 `field` 有預設值 `PropertyField::None`。
  Pad 的 Length 那一列是用**七個參數**的 aggregate 寫出來的，
  於是 `field` 靜靜地落在 `None` 上——而 `ApplyPropertyEdit` 對 `None` 的回答是
  「that row is not editable」。

  結果是一個**沈默的空操作**：儲存格看起來可以編輯、接受輸入、
  把使用者打的數字留在畫面上，而文件從頭到尾沒有變過。
  沒有任何一步是壞掉的——每一步都照著自己的合約做事。
  受影響的有五列：Pad 的 Length、Pocket 的 Depth、Fillet/Chamfer 的尺寸、
  Revolve 的 Angle，以及**每一個尺寸約束的值**。

  為什麼所有測試都是綠的：既有的測試全部**自己挑 field** 傳給 `ApplyPropertyEdit`，
  而面板不是這樣做的——面板讀的是 `DocumentOutline` 建好的那一列上的 `field`。
  測試從來沒有走過那條接縫。

  修法不是把 `PropertyField::Value` 補在五個地方，而是**讓它不可能再被忘記**：
  五個呼叫點現在都經過 `EditableValueRow(group, label, parameter)`，
  **一個工廠沒辦法忘記它根本不收的參數**。
  M17_UI_060 用面板的方式驅動每一列（`row.field`，不是測試自己挑的），
  M17_UI_061 檢查「可編輯」的三個必要條件同時成立。

- **ADR-M17-028** — **在 3D 的面上建立草圖**：點一個平面，然後在它上面畫。

  3D 檢視的選取模式從「整個物件」改成 **`TopAbs_FACE`**，
  這推翻了 ADR-M4-004 中「只做整體選取」的那一半。
  物件選取並沒有因此消失：`SelectedInteractive()` 仍然把被點到的面
  解析回它的 `AIS_Shape`，ObjectId 的查表照舊——多出來的只是**知道是哪一個面**。

  **草圖放在那個面當下所在的「平面」上，而不是綁在那個面上。**
  這是刻意的限制，不是遺漏：要讓草圖跟著面走，需要一個能在重建之後
  仍然指得到同一個面的名字——也就是拓樸命名問題（roadmap 20）——
  而這個專案還沒有那套命名。誠實的選項只有兩個：
  「放在平面上並且說清楚」，或「等命名做好」。
  假裝有面的參照、然後在事實證明沒有的時候悄悄把使用者的幾何搬走，從來不在選項裡。
  **成功訊息本身就會講這件事**，因為限制是功能的一部分，
  不該是某份沒人會打開的文件裡的一行字（M17_FACE_008 就是在盯這句話）。

  三個約定，每一個都有理由：
  - **原點** = 零件原點投影到該平面上。不是面的中心——面的中心會隨著面被改大改小而移動，
    同一個面上的同一次點擊在編輯之後就會給出不同的 (0,0)，
    使用者從原點量過的每一個尺寸都會變成別的意思。
  - **v 軸**盡可能指向世界 +Z，所以在垂直面上畫圖時，「上」就是看起來的上。
    水平面上這條規則沒有答案，於是 u 取世界 +X——
    這讓「在方塊頂面上畫圖」和「在世界 XY 平面上畫圖」讀起來完全一樣。
  - **法線保留面的 orientation**。每個實體都有一半的面是 `TopAbs_REVERSED`，
    忽略它會讓平面是對的、方向錯一半——而方向決定了 Pad 是長出去還是長回材料裡面，
    後者在畫面上看起來就像「按了沒反應」。

  分層照舊：`PlaneOfFace` 放在 kernel 層（`OcctFaceQuery`）而不是 widget 裡，
  因為這樣測試可以用真的 kernel 造一個真的方塊來問它（M17_FQ_002 就是這樣抓法線的）；
  判斷的部分（能不能畫、原點在哪、u/v 怎麼走）在 Qt-free 的 `FaceSketch`，
  widget 只剩下「問 context 點到了什麼」這件真的需要滑鼠的事。

- **ADR-M17-029** — **投影參考幾何**：在面上開草圖時，把那個面的邊界投影進草圖畫面當底圖，
  並提供 **Use** 工具把投影出來的點／線／弧／圓轉成這個草圖真正能用的圖素。

  **參考不是圖元，而且它有自己的容器。**
  一個 `SketchReference` 沒有求解變數（求解器看不到它，它不會動）、
  不貢獻任何 profile 邊、也不能被任何約束指名。
  把它做成「帶第三個旗標的 entity」會讓它出現在每一個走訪 `entities_` 的迴圈裡——
  求解器、profile builder、序列化、畫布、undo——而那些地方就都得記得跳過它。
  **少跳過一次，就是一條參考邊悄悄變成實體的一部分。**
  分開的 vector 不會被忘記，因為它根本不會被誤闖。

  **投影要嘛完整，要嘛講清楚它不完整。**
  少了三條邊的底圖，看起來就跟一個少了三條邊的面一模一樣：
  使用者照著描，描出錯的輪廓，而整條路徑上沒有任何東西會報錯。
  所以每一條沒帶過來的邊都被計數並且分類說明：
  - **spline / ellipse**：kernel 回報的曲線 EP3D 沒有對應的圖元（各自是一個 milestone）；
  - **斜看的圓**：圓的平面和草圖平面不平行時，投影出來是**橢圓**。
    兩個看似合理的錯誤答案都是靜默的——用原半徑畫圓（太寬）或用短軸畫圓（太窄）——
    兩者都會產生一張看起來對、量起來錯的圖。所以是跳過並計數，不是近似；
  - **正對邊（edge-on）**：垂直於草圖平面的線會塌成一個點。點還是留著當抓取目標，線沒了，而且說出來。

  三個約定：**原點**沿用 ADR-M17-028（零件原點投影到平面上）；
  **頂點與圓心**都變成可抓取的點，並且**去重**——相鄰兩邊共用的角點只會有一個，
  否則使用者分不出自己抓到的是哪一個；
  **弧一律以逆時針儲存**，方向相反時交換兩端點（A 到 B 順時針 = B 到 A 逆時針，同一條曲線），
  這樣底圖裡的每一條弧都是草圖模型預期的那一種，
  而不是帶一個每個消費端都得記得處理的方向旗標。

  **Use 是一個模式，不是一個選取指令**，理由和 Trim 一樣：
  參考在選取模型裡根本沒有位置（它沒有 `SketchElementRef`，
  不能被約束、標註、拖曳或刪除），所以「要哪一條」只能用指的。
  反過來讓參考可被選取，等於讓上面那四件事都可以被嘗試在一個模型裡沒有身分的幾何上。

  轉換產生的是**一個普通的 AddPoint / AddLine / AddCircle / AddArc 編輯**，
  刻意不新增 edit kind：既有的 undo delta、標籤、狀態列措辭、
  以及失敗時乾淨回滾的交易，全部免費沿用。
  另一條「轉換專用」的建立路徑會是第二種造圖元的方法，兩者遲早會走鐘。

  **自動加的 Fix 只加到不會冗餘為止**：
  點、以及線的兩個端點——完全鎖住，線的 4 個自由度對 4 條 residual；
  圓和弧**只鎖圓心**。把弧的圓心和兩個端點都鎖住會是 6 條 residual 對 5 個未知數，
  求解器會正確地回報 over-constrained，並且指著一個使用者從沒加過的約束。
  半徑（和弧的掃掠角）留著自由，而且**訊息會明講**——
  讓使用者從 DOF 數字自己發現，等於是先騙了他一次。

  **同一條邊第二次是拒絕，不是複製**：兩條完全重疊的曲線在畫面上看不出來，
  卻會讓 profile 走訪在每個頂點都找到兩條出路。比較用的是草圖模型自己的 `IsSameCurve`，
  所以反向點第二次也認得出來。

  **持久化（v17）**：底圖跟著檔案走，理由和平面一樣——兩者都是「做這個草圖時那個面長什麼樣」的凍結快照。
  存檔、重開、想再描一條邊，卻發現底圖不見了、而且除了刪掉草圖重來之外沒有辦法拿回來，
  那不是一個能用的功能。沒有底圖的草圖**不寫** `references` 陣列，
  所以沒用到這個功能的檔案，位元組和 v16 完全一樣。

  **畫法用三個通道和真幾何區分，不是一個（A06）**：不同顏色、**點劃線**、以及較細的線寬。
  建構幾何已經是虛線，所以點劃線才是在黑白截圖裡分得出兩者的那一個——
  而分得出來很重要：建構線是草圖的一部分，參考不是。
  頂點畫成小方框而不是真 Point 的十字，理由相同：
  使用者要能一眼看出哪些點已經能約束，哪些得先轉換。

- **ADR-M17-030**（缺陷 + 功能，皆由 owner 執行程式後回報）—
  **一個 struct 被抄成兩個**，以及**草圖要畫在 3D 零件視圖裡**。

  **缺陷：投影完全沒有出現。**
  `OcctViewWidget::readPickedFace()` 把 kernel 的 `FacePlane` **逐欄位手抄**
  進 viewer 自己的 `PickedFace`——抄了四個純量欄位，**漏掉第五個 `boundary`**。
  於是 kernel 讀出了面的每一條邊、viewer 把它們丟掉、投影拿到一個空邊界、
  畫布畫了零個項目。**每一層都是對的，功能不會動，1287 個測試全綠。**

  為什麼沒有測試抓到：兩邊的測試各自建構自己的資料。
  kernel 測試用真的方塊問 `FacesOf`；投影測試自己造 `PickedFace`；
  shell smoke test 因為沒有 3D 點擊，直接用 façade 塞參考幾何進去。
  **沒有任何一個測試跨過那條接縫。**
  更糟的是，整合測試裡的輔助函式**重現了同一個手抄**——
  一個複製了production bug 的測試，永遠抓不到那個 bug。

  修法不是補一行複製，而是**讓那條接縫消失**：
  `FacePlane` 本來就沒有提到任何 OCCT 型別，所以它搬進 Core，
  `PickedFace` 變成它的 `using` 別名，widget 改成**一次整體指派**。
  **一個定義不會和自己不一致，也不會忘記之後新增的欄位。**
  新的測試（M17_E2E_004/005）從真的 OCCT 面一路走到投影出來的圖素。

  **功能：草圖畫進 3D 視圖。**
  草圖只活在 2D 畫布上時，它只有一半可見：使用者按下 Finish Sketch、
  回頭看零件，看不到這個草圖相對於其他東西在哪——
  而那正是草圖之所以有「平面」的全部理由。

  用**線架構**繪製，顏色也不同，因為草圖不是實體、不該讀起來像實體；
  顏色不是唯一通道——草圖沒有面，無論怎麼著色都看得出是一組曲線。

  **被 Pad 消耗掉的草圖仍然會畫**，這一點和被消耗的實體**刻意不同**：
  被消耗的實體是同一塊材料的舊版本，畫出來會把後繼特徵的凹槽視覺上抹掉；
  而草圖和它長出來的實體是兩個不同的東西，
  在面上看到那圈輪廓，正是使用者確認 Pad 做對了的方式。
  不同意的人有 Ctrl+H。

  `BuildSketchWireframe` 放在 kernel 層而不是 widget 裡，理由和 `PlaneOfFace` 一樣：
  這裡唯一會出錯的事情是**把傾斜面上的草圖畫成平躺在世界原點**——
  在 2D 畫布上看起來完美無缺（畫布只認 (u,v)，從不問平面在哪），
  只有 3D 視圖看得出來。所以新增了 `BoundsOf` 這個 kernel-neutral 的門，
  讓測試不用碰 OCCT 型別就能問「它到底跑到哪去了」（M17_WIRE_002/003）。

  **草圖工具列拆成兩排。**
  建立它的註解寫著「十八個按鈕」，那句話當年是對的；現在是 **36 個**。
  Qt 對「比視窗還寬的工具列」的處理方式是把溢出的按鈕收進一個小箭頭裡——
  所以在任何正常的視窗寬度下，**最後三分之一的草圖工具根本不在畫面上**。
  owner 找不到 Use 按鈕，那是對「一個不在螢幕上的按鈕」唯一正確的反應。

  拆分在工具列**建好之後**做，而不是讓二十幾個 `addAction` 各自選一排：
  二十幾個呼叫點各自選擇，就是二十幾個讓新命令落錯排的機會，
  而且兩排會隨著命令增加而漂移。切點取**最靠近中間的分隔線**，
  落在工具列作者本來就認為是邊界的地方。
  所有 readback 都改成**橫跨兩排**——否則「每個圖示都不同」這個檢查
  會從此只看一半的圖示，而那正是最不能只看一半的檢查。

- **ADR-M17-031**（缺陷，由 owner 回報：「在側面上畫圓，Pad 可以，Pocket 不行」）—
  **擠出距離改為有號**，並在屬性面板上以 **Reversed 核取方塊**呈現。

  **兩個各自正確的約定撞在一起。**
  在面上建立的草圖，法線指向**實體外面**，這樣 Pad 才會往零件外面長（ADR-M17-028，
  M17_FACE_004 就是釘這件事）。
  而 Pocket 的刀具沿著**同一個 +法線**擠出（ADR-M8-002）——
  那個約定成立於「草圖躺在世界 XY 平面、Pad 往上長」的年代，
  當時草圖平面在材料**底下**，+法線正好切進去。

  從面草圖出發，同一條規則把刀具整個蓋在**材料外面**：
  布林運算成功、切掉零體積、feature 回報 Valid。
  **Pad 會動、Pocket 不會動，而且沒有任何錯誤訊息。**

  **修法：距離帶正負號。** 負值表示「長到平面的另一側」。
  這需要一個新的述詞 `IsValidSignedExtrusionDistance`，
  而不是放寬既有的 `IsValidExtrusionDistance`——
  因為後者同時守著**圓角半徑**和**倒角距離**，那兩個的負值毫無意義，
  放寬共用的那一個會靜靜地接受一個 -2 mm 的圓角。

  真實 kernel 測試（M17_KERNEL_042）證明反向擠出的體積是**正的**且大小相同：
  這裡有兩種同時出錯的可能——實體落在正確的一側但**方向反轉**，
  OCCT 會把它報成**負體積**，然後每一個下游的質量讀數都會照抄。

  **「切不到東西」是合法的，所以不在 Core 失敗。**
  第一版讓 PocketFeature 在體積沒減少時失敗，結果打翻了 M8 的一個
  **刻意決定**：release gate 用一個環形零件證明「刀具落在孔裡、合法地切掉零體積」
  不是錯誤（ADR-M8-002）。單靠體積分不出「合法的不相交」和「方向反了」。
  所以訊息改放在**指令層**：Pocket 指令在建立前後量一次體積，
  沒切到東西就把狀態列換成
  「Pocket created, but it removed no material ... type a NEGATIVE Depth to cut inward」。
  Core 允許什麼沒有改變，改變的是使用者讀得到什麼。

  **屬性面板：Reversed 是一個核取方塊，不是第二個欄位。**
  owner 建議「加一個 reverse 參數」——方向確實該有個能點的控制項，
  但**不該有第二份狀態**。一個獨立的 `reversed` 旗標會是同一件事的兩個真相：
  使用者在 Length 打了負號之後，那個旗標仍然寫著「forward」，
  而 feature 會往兩者都沒有要求的方向長。

  所以這一列**讀的是符號、寫的也是符號**：
  `PropertyField::Reversed` 沒有自己的儲存空間，
  它指向的 `parameterId` 就是 Length／Depth 那一列指向的同一個參數。
  一件事，用使用者能操作的形式呈現——
  「深度 -5 mm」讀起來很怪，「Reversed ☑」不會。
  M17_UI_072 釘的正是這一點：在 Length 打 -20，方塊必須**已經**是勾的。

  兩個拒絕：**零沒有方向**（翻轉零的符號只會讓 feature 一樣壞掉，
  而使用者只會看到一個勾），
  **被運算式驅動的值不翻轉**（`setParameterValue` 的第一個動作是清掉運算式，
  ADR-M11-006——所以偷偷翻轉會讓面板和公式各說各話，而且公式會無聲消失）。

  受影響的既有測試都是**用負值當作「製造失敗」的手段**：
  M4_PAD_022、M4_KERNEL_041、M8 的 GATE_E/E2/E3/RD、M9 的 GATE_E5/G4/H。
  它們關心的是失敗如何傳播，不是哪個值無效，所以一律改用 **0.0**——
  值是槓桿，不是主題。每一處都加註了為什麼負值離開了那份清單。

- **ADR-M17-032** — **View 選單新增 Solid / Wireframe**。

  兩個 **checkable 且互斥**的項目（放在同一個 `QActionGroup` 裡），
  不是兩個獨立命令：它們是同一個設定的兩個狀態，
  一個把兩者都打勾的選單，描述的是這個檢視器不可能處於的狀態。
  那個勾也是**目前模式唯一被寫下來給使用者看的地方**——
  在有實體的時候著色與線架構一眼可辨，但在還沒有實體的文件上完全看不出來。

  **只影響實體，不影響草圖。**
  草圖永遠是線架構（ADR-M17-030）：它沒有面，「著色」對它無話可說，
  而把整個場景一起切換，會讓唯一不能著色的物件在著色模式下看起來像壞掉。

  切換時是對**場景裡既有的 presentation** 套用新模式，而不是重建場景：
  重建會把選取狀態丟掉，而「換一種畫法」不構成「停止選取」的理由。

  狀態一律**從 viewer 讀回來**，不假設：
  一個自己打勾、而檢視器做別的事的選單，
  和草圖工具列曾經出過的那個缺陷是同一個，只是換了衣服。
  變異測試把 `solidDisplay_ = mode` 拿掉之後，shell smoke test 三條同時變紅——
  包括「檢視器在線架構、選單卻不說」這一條。

- **ADR-M17-033** — **模型樹改為「時間軸 + 吸收」**（SolidWorks 的排法）。

  舊的樹先列出**所有草圖**、再列出**所有 feature**。
  在面上畫、Pad、在新面上畫、再 Pad，得到的是三個草圖排一起、三個 Pad 排一起：
  **順序消失了，而且沒有任何東西說哪個草圖做出哪個 Pad。**
  這兩件事一直都在模型裡，只是樹沒有顯示。

  **順序：照 ObjectId 排。**
  這份文件裡每一個 id 都來自同一個 `ObjectIdGenerator`，
  所以 id 的順序**就是**建立順序——包括重新載入之後，
  因為 restore 會保留每個 id 並把產生器推進到它之後。
  照 id 排序因此不需要在任何地方存時間戳，也不可能和「東西實際被做出來的順序」不一致。

  **吸收：草圖畫在消費它的 feature 裡面。**
  這是 SolidWorks 的做法，不是 Onshape 的。
  Onshape 把草圖留在同一層、完全平鋪；SolidWorks 把它收進 feature 底下。
  選 SolidWorks 是因為**血緣關係要出現在使用者會看的地方**，
  而不是藏在一個沒人會打開的依賴關係對話框裡。

  **被兩個 feature 共用的草圖，不吸收。**
  把它塞進其中一個底下，等於宣稱它屬於那個 feature——
  對另一個來說那是假的，而且使用者沒有任何辦法看到被樹藏起來的那個關係。
  它留在主幹上，明顯地不屬於任何一邊。

  **「哪個草圖」用 capability 問，不用型別問。**
  新增 `ISketchConsuming`。`featuresReferencingSketch` 曾經只列舉 Pad，
  是在 Pocket 和 Revolve 都已經出貨之後才被 review 抓到的——
  那讓那個函式自己的合約（「空集合正是這個草圖可以被刪除的條件」）
  對三種之中的兩種都是假的，而且是 UI 刪除路徑上的一把上了膛的槍。
  當時的修法是再加兩個分支，那等於把同樣的陷阱留給第四種。
  **問 feature 自己就不會過期**：一個新的消費草圖的 feature
  要嘛實作這個介面、於是到處都找得到它，要嘛不實作、於是到處都找不到——
  而「到處都找不到」是它作者在編譯期做的決定，
  不是別人在程式碼另一端忘記加的一個分支。

  **一個吸收暴露出來的既有缺陷。**
  `rollUp` 會把節點的狀態覆寫成「自己和子節點裡最糟的那個」。
  草圖被吸收之後，一個因為草圖有衝突尺寸而 **Blocked** 的 Pad
  （它根本沒跑，壞掉的是草圖）就被子節點的 Failed 覆寫成 **Failed**——
  **正是 M5_DEF_012 存在的目的所要保護的那個區別，在它當初為之而寫的那個情境下被摧毀**，
  然後把使用者指向錯的物件。

  規則改成：**只往「自己沒有狀態」的列彙總**。
  容器（根節點、Parameters、Frames）是 Normal，因為它們沒有東西可以計算，
  彙總是它們唯一能說的話；
  而一個 feature 的狀態是**關於那個 feature 的事實**，
  底下有什麼的摘要不可以覆寫那個事實。
  最糟的狀態仍然會**往上傳遞**，只是不再覆寫有話要說的列。

- **ADR-M17-022（補完，M17.11）** — Fillet 與 Chamfer 也回報**自己的**診斷。

  ADR-M17-022 在 Pad、Pocket、Revolve 上修掉了「不管 kernel 做了什麼都印 created」
  這件事，**但 Fillet 和 Chamfer 一直沒改**：兩者都硬寫著
  「Fillet created; edit its Radius in the panel」。

  遇到它的方式很日常：**圓角半徑大到幾何吃不下**。
  kernel 拒絕、feature 變成 Failed、實體一動也沒動，而指令說「建立成功」。

  兩者現在都走 `describeCreatedFeature`——和另外三個同一條路。
  smoke test 把零件壓到 2 mm 厚，讓預設的 2 mm 半徑無處可去，
  然後檢查指令有沒有講出來（變異驗證：把訊息換回硬寫的字串，兩條檢查同時變紅）。

- **ADR-M17-034** — **邊選取存「查詢」，不存邊**（Onshape 的架構，不是 SolidWorks 的）。

  M8 當初把「選邊」延後，理由寫得很清楚：能拿來當名字的只有 OCCT explorer 的位置，
  而那是 ADR-M4-004 明文禁止當識別的暫態拓樸。這一版做的就是它在等的那個東西。

  **fillet 不記得「第 7 條邊」，它記得一句關於自己要哪些邊的話**，
  而那句話在**每次重算時重新回答**。
  差別在參數一改就看得出來：索引指向的是「現在剛好排第七的那條」——
  重算之後那是另一條邊，或者根本不存在，於是圓角要嘛失敗、要嘛**無聲地跑到別的地方**。
  「頂面的那些邊」在零件長高之後仍然是同一句話，因為它從一開始就沒有在描述位置。

  這也是為什麼**沒有任何一個查詢存下當時的座標**。
  一個「z = 20 的平面」只是穿了好衣服的索引：把墊片改成 30 mm 高，它什麼都比對不到。
  目前的三種都寫成「答案會跟著模型走」的形式：
  `AllEdges`、`EdgesOfExtremeFace{方向}`（外側面）、`EdgesParallelTo{方向}`。

  **比對不到任何邊 = 失敗，而且把那句話唸出來。**
  一個沒有修飾到任何邊的 fillet 會原封不動地回傳實體並回報成功——
  又一個「說有做、實際沒動」的指令，這個專案已經換過兩次衣服遇到它了。

  **點面轉查詢時，說不出來就拒絕。**
  今天的詞彙只有「某方向最外側的面」。
  使用者點的如果是凹槽底面（它也朝 +Z，但不是最外側），
  那句話講的是頂面而不是他點的那個面——所以**拒絕**，並說明缺的是詞彙而不是他做錯。
  存下最接近的那句話，會在下次重算修飾錯的邊，而且看起來像是有意為之。

  `filletAllEdges` / `chamferAllEdges` 被**取代**而不是並存：
  `AllEdgesSelection()` 講的是同一件事，而同一個行為有兩種說法，
  正是兩種行為最後會冒出來的原因。

  持久化 v18，非預設才寫，所以既有的每一個 fillet 位元組不變；
  **空陣列被拒絕**而不是讀成「所有邊」——那是兩個相反的實體。

- **ADR-M17-035** — **第 0 階段（消滅接縫）與 `CreatedBy`（來歷查詢）**。

  **接縫**：這一輪的缺陷全都是同一個形狀 ——
  兩個東西必須一致、中間靠人手抄或靠一份清單，而各自的測試都不會發現不一致。
  這次動手清掉三個：

  - **`FeatureData` 併入 `FeatureSnapshot`**。序列化的 loader 本來有一個
    十八個欄位的平行 struct，下面十八行把一個抄進另一個。
    這正是 `FacePlane` / `PickedFace` 那個 bug 最素的樣子 ——
    往其中一邊加第十九個欄位，載入時就會靜靜掉。現在只有一個 struct。
  - **`m4-circle-r10`、`m4-circle-r20`、`m4-failed-profile`** 三個樣本
    指令列接受、但 CI 從來沒跑過：**應用程式進得去、而沒有東西進去過的狀態**。
  - **草圖工具列的分排**從「取最靠近中間的分隔線」改成**語意邊界**
    （上排畫與約束、下排修改）。前者是關於算術的事實，不是關於命令的事實，
    每加一個按鈕就會漂移。

  **`CreatedBy`**：形狀現在帶著「誰造了哪個面」。
  這是唯一一種**描述來歷而不是描述形狀**的查詢，
  因此也是唯一一種**幾何移動之後仍然成立**的查詢 ——
  「口袋切出來的東西」在口袋被加深、加寬、或整個搬走之後，還是同一句話。

  它也是**唯一能指名內部面的方式**。「+Z 方向最外側的面」是頂面，不是凹槽底面，
  所以在這之前，凹槽自己的邊**根本沒有辦法被選取**，
  而「把凹槽內側倒個圓角」是最普通不過的需求。

  記錄的方式刻意**不穿過 `IGeometryKernel`**：
  把 tag 塞進 extrude、revolve、subtract、fillet、chamfer 五個簽章，
  等於把一個文件層的概念推進五個 kernel 介面和每一個假 kernel，
  而那五個運算沒有一個需要它才能造出幾何。
  改成事後比對 base 和 result —— OCCT 的布林**和輸入共用 TShape**，
  所以「運算沒動過的面」就**是**base 那個面，不是它的副本。
  key 是一個不透明的 `std::uint64_t` 而不是 `ObjectId`：kernel 拿到什麼數字就還什麼數字。

  **改選擇必須弄髒 feature。** 第一版的 `setEdgeSelection` 是 public，
  結果一個設了三種不同選擇的測試拿回三個**一模一樣**的實體 ——
  選擇變了、圖沒重算、上一個選擇的形狀被當成現況交回去。
  現在它是 private、`friend class PartDocument`，
  唯一的入口 `setFeatureEdgeSelection` 會標記 dirty。
  「只有 document 該呼叫它」曾經是 `IMaterialReferencing` 裡的一句註解，
  而註解不強制任何事；現在由編譯器說。

  **序列化的 `else` 分支**：`WriteEdgeQuery` 原本是 if/else 鏈，
  最後一個 `else` 直接取第三種。變體長出第四種之後，
  那個 `else` 會去拿錯的一種並在**存檔時丟例外**——
  一個造得出來、寫不下去的文件。改成 `std::visit` + `if constexpr`，
  少一種就**編譯不過**，而那才是這種失敗該發生的地方。

- **ADR-M17-036** — **`FaceQuery`、草圖跟隨面、查詢組合**（第 1 階段完成）。

  **`FaceQuery` 是合取，`EdgeSelection` 是聯集** —— 兩種形狀，兩個理由。
  選一組邊是「這些，再加上那些」；指名**一個**面是「一直縮到只剩一個」。
  合取正是「口袋切出來的東西的**頂面**」唯一講得出來的方式：
  `createdBy` 單獨用會同時指到底面和四面牆，
  `extremeTowards` 單獨用指的是零件自己的頂面，
  只有兩個一起才指到凹槽底面。

  **模糊是拒絕，不是挑一個。**
  兩個面在同一個距離、朝同一個方向，那是一個對稱零件；
  隨便挑一個會把答案放在使用者既無法預測、也無法修正的地方 ——
  而如果那個答案是一個草圖的平面，整個模型就蓋在錯的地方。
  訊息帶著**數量**，因為修法是「再加一個條件」，使用者需要知道自己差多遠。

  **草圖真的跟著面走了。** ADR-M17-028 當初只能凍結平面，
  因為沒有任何詞彙能描述一個「重建後仍然指得到」的面。現在有了。
  把墊片改高，畫在頂面上的草圖**跟著升上去**，蓋在它上面的 Pad 也跟著。

  三個一起才成立的細節：
  - **重新求解排在 recompute 的最前面**。求解是在 (u,v) 裡做的，
    而平面是把 (u,v) 變成位置的東西 —— 先解再搬平面，
    會得到「這一次的幾何長在上一次的平面上」，而下游沒有任何東西看得出來。
  - **`setSketchTrackedFace` 先加圖的邊，再存查詢**。
    `addDependency` 是唯一會拒絕循環的地方；反過來做會留下一個
    「圖不支援的查詢」躺在草圖裡。
  - **面不見了要大聲失敗**。保留上一次的平面然後繼續，
    等於讓幾何待在模型已經不再宣稱它屬於的地方，而且沒有任何東西會說。

  **載入順序的坑**：第一版在還原草圖時就套用 trackedFace，
  但 feature 是在草圖之後才還原的，於是 façade 每次都拒絕，
  而拒絕被**無聲丟掉** —— 檔案說草圖跟著面，載進來的文件說它沒有。
  現在延後到 feature 存在之後，而且**拒絕會讓載入失敗**：
  一個「說自己跟著某個面、而那個面跟不了」的檔案，
  行為會和它自己寫的不一樣，安靜地丟掉追蹤正是它會怎麼不一樣。

  `SketchFrame::OnFace` 把「這個面上哪邊是上」搬進 Core 成為**單一轉換點** ——
  建立面草圖的指令和重新求解都用它。兩份會讓草圖在第一次重建時跳一下。

- **ADR-M17-037**（缺陷，由 owner 提問「model tree 刪除之後可以 undo 嗎？」發現）—
  **能不能 undo 是從模型讀出來的，不是照型別猜的**；以及 `FeatureSnapshot` 的第二個生產者。

  Core 早就分成三種情況：**參數、frame、connector、以及沒有被下游消耗的 feature**
  會被記錄，undo 拿得回來；**被消耗的 feature、草圖、body、材質**沒辦法重播，
  所以整段歷史**被清空**，而不是留下一個會做錯事的 undo。

  `removeObject` 自己的註解寫著：清空**是可觀察的**——
  「**so a UI can tell the user the history ended rather than offering an undo that lies**」。
  **沒有任何 UI 這樣做過。** 這個指令只警告草圖，
  所以刪掉一個被消耗的 pad、一個 body、或材質，
  會把使用者累積的每一步 undo 一次抹掉，然後說「Deleted」。

  現在訊息從 `undoDepth()` 的前後差讀出來，三種各自照實說 ——
  包括第二種損失，也就是真正會痛的那個：
  不只這次刪除救不回來，**先前每一步也一起變成永久的了**。

  **順帶抓到的**：`FeatureSnapshot` 有**兩個生產者** ——
  `SnapshotFeature`（記憶體）和 JSON loader —— 而 `edgeSelection` 只到了後者。
  刪掉一個選了面的 fillet 再 undo，它會**變回修飾所有邊**：
  實體變了，而沒有任何東西說。
  這和 M17.13 併掉的那個手抄是同一件事的另一面：
  併掉 `FeatureData` 解決了 loader 那一側，
  但這個 struct 的另一個生產者當時沒有一起看。

- **ADR-M17-038**（缺陷，由 owner 的 `as.ep3d` 直接證實）— **名字必須唯一**。

  owner 的檔案是 **Pad(31) → Pocket(57) → Pocket(81)**，
  而兩個 Pocket 在樹上**都叫「Pocket」**。
  用他的檔案實測：刪 57（中間那個，被 81 消耗）`undo 1 → 0`，歷史清空；
  刪 81（鏈尾）`undo 1 → 2`，可以還原。

  **兩者不可互換，而畫面上沒有任何東西分得出來。**
  這不是好不好看的問題：樹是使用者用來挑「要刪哪一個」的唯一依據。

  **參數那一半更嚴重，而且是正確性問題。**
  兩個 Pocket 各自建了一個叫 `PocketDepth` 的參數。
  運算式是**按名字**解析參數的，而 `findByName` 回答的是**第一個**符合的 ——
  所以任何 `#PocketDepth` 都會綁到先建立的那一個，
  而屬性面板上兩列長得一模一樣，使用者也看不出自己在編輯哪一個。

  `uniqueObjectName` 從 1 開始編號、跳過已被佔用的，
  所以刪掉 Pocket2 再新增一個會拿回 Pocket2，而不是無止境地往上爬。

  **順帶修掉一個測試裡的相同毛病**：smoke test 用字面名字
  `findByName("RevolveAngle")` 找參數 ——
  它宣稱在檢查「revolve 的角度」，實際上檢查的是**命名慣例**。
  改成問 feature 自己的 `angleParameterId()`。

- **ADR-M17-039** — **改名**：屬性面板的 Name 那一列可以編輯。

  ADR-M17-038 讓新建的東西名字唯一，但**既有檔案裡的名字沒有辦法改** ——
  owner 的 `as.ep3d` 裡兩個 Pocket 仍然同名，而唯一的補救是刪掉重做。

  **一個 delta，五種物件。** `ObjectNameEdit` 拿的是純 `ObjectId`，
  不是各型別自己的 id：名字是它們唯一共同擁有的屬性，
  每種一個 delta 會是同一個想法的五份副本，而第五份就是沒人補的那一個。

  **`setName` 在五個型別上都是 private + `friend class PartDocument`。**
  改名是一個 undo 步驟、而且必須拒絕重名；兩個決定都在 `renameObject` 裡，
  公開的 setter 會是繞過兩者的路。這個檔案裡其他寫入名字的規則也都是這樣執行的，
  而不是寫在註解裡。

  **拒絕重名不是龜毛**：對參數而言那是正確性問題（ADR-M17-038），
  而改名是現在唯一還能製造出重名的途徑，所以它是唯一必須擋的地方。
  前後空白會被修掉 —— 「Pad001 」和「Pad001」在樹上分不出來。

  **不弄髒任何東西**：名字沒有幾何後果，
  標記為 dirty 會讓底下整條鏈重算，然後產生一模一樣的形狀。

  **Name 那一列的 `parameterId` 裝的是「物件」的 id**。
  那個欄位的意思一直是「要寫到哪裡」，只是先前用它的全都在寫 Parameter ——
  所以 `ApplyPropertyEdit` 必須**先**回答 Name，
  否則每一個草圖和 feature 的改名都會被「that parameter no longer exists」擋掉。

  新增的 `typeIntoPropertyRow` readback 是為了回答第二個問題：
  既有的 readback 回答「面板**顯示**什麼」，這個回答「打字進去**有沒有用**」——
  那是兩個主張，而它們之間的落差正是 ADR-M17-027 那個
  「接受輸入、什麼都沒改」的 Length 列活了一個 milestone 的原因。

- **ADR-M17-040** — **四個新的放置方式**（第 2 階段便宜的那批，第一批）：
  中心矩形、三點圓、三點弧、正多邊形。

  **每一個都是不同的「點擊方式」，不是新的圖元型別。**
  中心矩形做出來的就是角落矩形做出來的那四條線；
  多邊形是畫在建構圓上的線。求解器不需要學任何新東西 ——
  這是它們排在橢圓和雲形線之前的原因。

  **中心矩形**：中心只是你點的地方，**不是一個約束**。
  說清楚很重要：期待「改大小時中心不動」的使用者，
  期待的是一個不存在的約束，而目前沒有中心線可以掛。

  **三點圓／三點弧**：三點共線會**拒絕**，而不是做出一個半徑近乎無限的圓 ——
  那個東西看起來像直線，而且會弄壞每一個碰到它的 profile。
  弧的**第三點決定往哪邊繞**：任兩點之間有兩條弧，第三點就是這個工具存在的全部理由。
  儲存時一律轉成逆時針（模型其他地方都這樣假設），需要時交換兩端。

  **多邊形是真的正多邊形**，而且 DOF 說得出來：
  n 條邊帶 4n 個自由度、圓帶 3，共 4n+3；
  角點重合吃 2n、每個角一個點在圓上吃 n、n-1 個等長吃 n-1，共 4n-1 —— 剩下正好 **4**：
  圓心、半徑、旋轉。那就是一個正多邊形，不多不少。
  外接圓是**建構幾何**：它出現在實體裡會是一條沒人畫過的曲線。

  **兩個陷阱是做的時候踩到的：**

  1. **在別人的交易裡呼叫用 `ScopedTransaction` 的 façade 會回滾整批。**
     第一版用 `setSketchEntitiesConstruction` 把圓標成建構，
     而那個 façade 開了 ScopedTransaction；
     它是 `owned_` 感知的（外層已經開著就不再開一次），
     但**沒有明確 commit 的東西，解構子一律 abort** ——
     於是它把 `ApplySketchEdit` 剛畫好的每一條線一起丟掉。
     （M17.19 又踩了一次同一件事，那次是自己寫的 façade 忘了 `transaction.commit()`：
     旗標設了、delta 記了，然後整個消失。**這個型別的預設是「丟棄」，不是「保留」。**）
     改成 `addSketchEntity(..., construction)` 一步做完，
     而且那個旗標現在也進了 undo delta —— 否則 undo/redo 之後外接圓會變成真的邊。

  2. **`PendingConstraint` 只認得四種**（H/V/Coincident/Fix）。
     多邊形要的 PointOnObject 和 Equal 直接掉進最後的拒絕，
     而訊息說「the sketch refused an automatically added constraint」——
     講的是一個**根本沒有被交給 sketch 的約束**。
     現在補上那兩種，並且**不認得的種類會明確說出是哪一種**，
     因為那是程式的錯，不是使用者的。

- **ADR-M17-041** — **標註工具**：點幾何，然後點標註線要放的位置（owner 提出，比照 Onshape）。

  先前是**先選取、再按八個標註按鈕之一**，位置由程式決定，事後才能拖。
  新的是一個**模式**：點幾何 → 種類從你點到什麼**推論**出來 → 再點一下決定位置。

  **種類走的是既有的 `requestDimension`**，也就是那八個按鈕用的同一個函式 ——
  工具和按鈕因此不可能對「這個選取是什麼意思」有不同看法。
  一條線是長度、兩個點是距離、圓是直徑，這張表本來就在 roadmap 7.1 裡。

  **「可以標了」就表示「下一下是放置」**，包括點在幾何上 ——
  這是 Onshape 的行為，也是唯一不會要求使用者「去找一塊空白處才能結束」的規則。

  **會先畫出來給你看。** 選取一旦足以構成標註，游標處就畫出一個虛線的預覽 ——
  否則等於要使用者替一個看不見的東西決定位置，然後事後才能檢查。
  預覽刻意畫得樸素：它要說的是「會放在哪」，
  一個和成品長得一樣的預覽會讓人不確定自己是不是已經按下去了。

  **Esc 分兩段退**：先丟掉已經點的幾何，沒有半成品時才離開模式 ——
  一次按鍵不該同時丟掉兩件事。

  **一次擺放是一個 undo 步驟。** 第一版把位置寫在 `ApplySketchEdit` 的交易**外面**，
  於是變成兩步：Ctrl+Z 只把標註移回自動位置、然後留在那裡 ——
  那不是任何人說「取消我剛放的標註」時的意思。
  位置現在由 `SketchEdit` 帶著，在同一個交易裡寫入
  （`setSketchDimensionPlacement` 只 recordDelta、不開自己的交易，所以安全 ——
  和 ADR-M17-040 那個 `ScopedTransaction` 陷阱剛好相反，值得一起讀）。

  **那八個按鈕還在。** 它們做的是**明確指定**種類（同樣兩點，你要的是水平距離而不是直線距離），
  而這正是新工具刻意不猜的那件事。

- **ADR-M17-042** — **參考尺寸**：一個**量測**而不驅動的標註。

  **一個旗標，不是一個新種類**，理由和 entity 的 `construction` 一樣：
  一個 driven 的 Length 仍然是 Length —— 指同一條線、顯示同一個數字 ——
  差別只在資訊往哪個方向流。
  一套平行的 driven 種類會讓求解器、序列化和面板裡的每一個 switch 都變兩倍，
  只為了表達一個布林值。

  **兩個主張，而且往相反方向失敗**：
  它必須**不吃掉任何自由度**（否則只是一個標籤令人困惑的普通尺寸），
  而它的數字必須**跟著幾何走**（否則是一個看起來很權威的過期數字）。
  兩者都有測試，而且是用**同一個草圖、同一個約束、只差一個旗標**量出來的。

  **量測只有一份公式。** 每個尺寸約束都有一條公式被 residual 驅動到零，
  而在此之前那條公式存在**兩份**：一份是 residual，
  一份是新標註的「種子值」（讓「加標註不會移動幾何」成立）。
  參考尺寸會需要**第三份**，而三份「這兩點之間的距離是多少」
  就是三個可能給出不同答案的地方 ——
  症狀會是「參考尺寸和驅動尺寸對同一段幾何報出不同的數字」。
  所以 `MeasureConstraint` 進了 Core，成為唯一一處。

  **量測寫在 commit 之後**：參考尺寸報告的是幾何**現在是什麼**，
  而幾何在 commit 之後才定案。提早量會發佈上一次求解的數字 ——
  一個看起來很合理的數字，也就是最糟的那種錯。

  **它的數字不能用打字改**：那是衍生值，
  一個「接受輸入、看起來變了、然後在下次重算被覆寫」的欄位，
  比一個直說自己不收的欄位更糟。

  **畫成括號**，那是製圖慣例、也是黑白列印保得住的通道（A06）——
  一個看起來在控制零件、實際上沒有的數字，比沒有數字更糟。

  **`ScopedTransaction` 又咬了一次**：這次是自己寫的 façade 忘了
  `transaction.commit()`。旗標設了、delta 記了，然後解構子把整批 abort ——
  函式回報成功、而什麼都沒發生。
  **這個型別的預設是「丟棄」**，而那正是它讓「中途放棄的 façade」安全的原因。
  ADR-M17-040 裡對它的描述當時寫錯了（說它會提交呼叫者的交易），已經一併更正。

- **ADR-M17-043** — **槽孔工具**，以及一個**寫出來而不是藏起來**的限制。

  兩個中心，再一下設定寬度。第三下用的是它到中心線的**垂直距離** ——
  沿著槽滑動不該改變寬度，而那正是拖曳時手會做的事。

  四個圖元：邊、端弧、邊、端弧，繞著輪廓走一圈。

  **DOF 原本是 9，不是 5。ADR-M17-044 把它修好了，現在測試釘的是 5。**

  一個槽孔有五個自由度（兩個中心、一個半徑），
  四個圖元帶著十八個，所以理想上要拿掉十三個。
  實際拿得掉的是**九個**：四個角落重合（8）加上一個等半徑（1）。
  **四個相切一個自由度都沒拿掉**，而那是那個約束的性質，不是這個工具的錯：

  `TangentLineCircle` 說的是「圓心到直線的垂直距離等於半徑」。
  而接觸點已經被重合約束釘在那條線上了 ——
  於是那個距離**永遠不可能超過半徑**，residual 停在一個極大值上、
  梯度消失，所以它無論多正確都拿不走任何自由度。
  「在**這一點**相切」需要另一種說法：直線方向垂直於該處的半徑。

  所以當時的槽孔**接得住**（兩端不會脫開），但在標註之前**會歪**，
  而 DOF 讀數誠實地說 9。硬釘 5 等於宣稱一個當時的詞彙做不出來的槽孔。
  **下一個 milestone 補上了那個詞彙**（ADR-M17-044），現在它是 5。

  **相切約束還是加了**，即使今天不承重 ——
  它們是真的、而且是對的；拿掉它們今天的草圖一模一樣，
  等到「在某點相切」的 residual 出現的那天卻會是錯的。

  **這一步已經做完**：`TangentAtPoint`，見 ADR-M17-044。

- **ADR-M17-044** — **在指定的點相切**，以及一個**關掉自己的守衛**。

  ### 一、那個不承重的約束

  `TangentLineCircle` 說的是「圓心到直線的垂直距離等於半徑」。
  當直線自由滑動時，這是對的方程式。
  當接觸點**已經被重合約束釘在那條線上**時，它是**錯的方程式** ——
  那個距離永遠不可能超過半徑，residual 停在極大值上、梯度消失，
  於是它**一個自由度都拿不走**，而且看起來完全滿足。

  換個說法就好：在**已知的那一點**，相切就是**垂直**。

  ```
  dot(far - touch, touch - centre) / (|far - touch| * r)
  ```

  兩邊都做正規化，所以它是兩者夾角的餘弦：無因次、上界為 1、
  在相切時恰好為零 —— 而且**在那裡的梯度不會消失**。

  `TangentConstraint::at` 記錄**是直線的哪一端**在接觸。
  `Whole` 表示「不知道」，也就是 M17.21 之前每一個相切約束的意思。
  它是**存下來的**，和 `internal` 同一個理由：
  如果改成從「現在有哪些重合約束」推導，
  那麼刪掉一個不相干的約束就會**默默改變**這一個的意思。

  **結果**：槽孔從 DOF 9 變成 5。圓角的相切從裝飾變成真的承重。

  ### 二、順手發現的：守衛把自己關掉了

  `SlotsRequired()` 對它的 switch 沒有涵蓋的 kind 回傳 **0**，
  而 0 和「這個方程式不讀任何變數」無法區分 —— 檢查迴圈根本不會跑。

  M17 加的**七個** kind（PointsDeltaU/V、PointLineDistance、
  SymmetricAcross/Along、ArcTipU/V）全部落在這個洞裡：
  arity 沒檢查，packing 也沒檢查。
  而那段程式碼的註解寫著「所以未來的 kind 不可能默默地
  從湊巧被塞進來的東西算出胡說八道」。**未來的 kind 就是這樣做的。**

  三個改動：

  1. `SlotComponent`（查表）換成 `SlotAccepts`（述詞）。
     必須這樣換，因為有一個 slot 合法地接受**兩種** component ——
     圓弧端點的角度對一端是 StartAngle、對另一端是 EndAngle，
     而同一個四槽公式服務兩者。**查表無法表達這件事，
     所以那兩個 kind 當初就被留在表外了** —— 洞就是這樣開始的。
  2. **沒列到的 kind 什麼都不接受**，所以漏掉一個會在第一次求解時大聲失敗。
  3. `SlotsRequired` 的 fall-through 回傳 `kUndeclaredArity = -1`，
     而求解器**拒絕**它，不再是跳過。

  一個測試走過整個 enum 的範圍（而不是走一份要有人記得去擴充的清單），
  確認每一個 kind 都宣告了 arity，而且每一個 slot 都接受某種東西。

  ### 三、關於 schema version 的一個接縫，順便補掉

  `"schemaVersion": 20` 這個字面值散在**五個**測試檔裡，
  所以每一次版本升級都會讓四個毫不相干的套件變紅。
  M17.19 那次就是這樣，前一次也是。

  現在 `CurrentSchemaVersion()` 從 header 匯出，
  測試用 `tests/Support/SchemaVersionText.h` 去問而不是去抄。
  **只留一個字面值**，故意的 —— 一個沒人注意到的版本升級值得一個警報，
  而一個拿自己跟自己比的常數不是警報。

- **ADR-M17-045** — **相切弧**，以及讓兩個曲線也能指定接觸點。

  ### 工具

  兩下。點一條線或一段弧的**自由端**，再點要停在哪裡。

  給定起點、該點的方向、以及終點，**只存在一條弧** ——
  所以沒有第三下要點，工具也沒有東西要猜。

  圓心必須落在起點的法線上（切線的半徑與它垂直），
  且與兩端等距。把圓心寫成 `p0 + s·n` 再解 `|p0 + s·n − p1| = |s|`：

  ```
  s = (d·d) / (2 · n·d),      d = p1 − p0
  ```

  `s²` 項對消，所以沒有開根號、也沒有第二個分支要選。

  會**接續**（像線段工具），所以可以連著畫一串。

  兩種拒絕，都帶著該怎麼做：
  - 第一下沒點到端點 → 「相切弧必須從線或弧的**端點**開始」。
    不會默默畫一條普通的弧 —— 那是本專案一直在付代價的**無聲代換**。
  - 第二下**正前方** → 圓心跑到無限遠，「用線段工具，或往旁邊點一點」。

  ### 兩個曲線在指定點相切

  ADR-M17-044 治好的病，`TangentCirclesOuter/Inner` 也有，而且是同一個原因。
  兩個**共點**的圓本來就滿足 `|r1 − r2| ≤ |C1 − C2| ≤ r1 + r2`
  （那是共點上的三角不等式）—— 所以外切式停在極大、內切式停在極小，
  兩者的梯度都消失。在相切附近，它們的成長是兩條半徑夾角的**平方**。

  夾角本身才是誠實的量法。在共點上，相切就是兩條半徑**共線**：

  ```
  cross(P − C1, P − C2) / (r1 · r2)
  ```

  夾角的正弦：無因次、上界為 1，而且導數在那裡正好是 1。

  **不需要內/外切的分支**。共線兩者都涵蓋，而草圖在哪一邊是由它現在的位置
  連續決定的，不是由一個求解器要遵守的旗標。
  那個旗標對「沒指定接觸點」的形式才重要 —— 正因為那個 residual 看不到接觸點。

  ### `at` 的意思擴大了一點

  現在它是「**`a` 的哪一個端點**」，不再只是「直線的哪一端」。
  線 + 曲線時 `a` 必須是那條線；曲線 + 曲線時 `a` 必須是一段**弧**
  （圓沒有端點，會被拒絕）。

  好處是相切弧工具只需要**一行**就同時服務兩種情況：
  把 host 放在第一個位置，這段程式碼不必知道它是線還是弧。

  ### 兩個被抓到的錯，都值得記下來

  1. **`TangentCurvesAtPoint` 第一版的 slot 順序是
     `(touch, c1, r1, c2, r2)`** —— 看起來比較整齊，
     但半徑放在 slot 4 會把後面所有 U/V 的奇偶性翻轉，
     於是有兩個 slot 被拿去跟錯的 component 比對。
     **ADR-M17-044 剛修好的那個守衛當場抓到它。**
     改法是「不要交錯」而不是「教述詞認識這個翻轉」：
     位置在前、兩個半徑在最後。

  2. **測試一開始只檢查「平行」**。一個把 host 方向反過來的突變體活了下來 ——
     它做出的是**互補弧**：同圓心、同半徑、同兩端，
     從接點**折返**回去。那是一個尖點，而它的正弦是乾淨的零。
     現在每一個平滑性斷言都成對：正弦要 ≈ 0，**餘弦要 > 0**。

- **ADR-M17-046** — **Split**，以及「切開之後，約束歸誰」這個問題的**明講版**。

  `PlanTrim` 自己的註解早就把這個問題寫在那裡了：

  > 「把中間那段拿掉會把一條線切成兩條，那是另一個操作，
  >  帶著另一個問題（**哪一半保留約束？**），而它不該用猜的。」

  這就是那個問題的答案。

  ### 三種判決，一個函式

  `SurvivesSplit` 對整個 variant **窮舉**，所以新增一種約束不可能拿到預設值。
  這裡特別重要 —— 猜錯是**無聲的**，而且要等到下次拖曳才會露出來。

  | 判決 | 意思 | 例子 |
  |---|---|---|
  | `EveryPiece` | 每一段都繼承這個性質 | 水平／垂直／平行／垂直於（線）；半徑／直徑／同心（弧） |
  | `OwningPiece` | 它指的是一個**點**，跟著那個點走 | 端點上的重合、固定、距離 |
  | `Refuse` | 它講的是**整體的長度或範圍** | 長度、等長、（未指定接觸點的）相切、點在物件上 |

  `Refuse` 會**擋下整個 Split 並且點名那個約束**。
  另外兩種無聲做法都是錯的：
  複製到每一段 → 要求兩條線都是原本的全長；
  默默丟掉 → 刪掉使用者親手打的尺寸。

  ### 一個新的原始操作，順手消掉一個接縫

  判斷需要知道約束用**哪一個子元素**指到目標 ——
  端點上的重合和整條線的水平，指的是同一個 entity、意思完全不同。

  `ReferencedEntities` 原本是一份**手抄的**欄位清單。
  現在只有一份：`VisitConstraintElements`（模板，const 與非 const 共用），
  `ReferencedElements` 讀它，`ReferencedEntities` 再從那裡導出，
  而 Split 用同一份去**改寫**目標。

  **ADR-M17-045 的 `at` 在這裡第一次真正發揮作用**：
  一個釘在端點的相切，如果報成 `Whole`，
  就會被讀成「關於整體」而擋下 Split ——
  但它其實只關於一個角落，而且應該跟著那個角落走。

  ### 幾何

  - 線／弧：n 個切點 → n+1 段。
  - **圓：n 個切點 → n 段弧**，不是 n+1 —— 封閉曲線的最後一段接回第一段。
    而且**一個切點打不開一個圓**（相切只碰一次），會被拒絕。
  - 端點上的切點**不算切點**：切下來是零長度，而且什麼都沒改變。

  相鄰兩段之間會加一個重合 —— **那就是 Split 和「刪掉再畫兩條」的差別**。
  刻意**沒有**加任何東西把切點綁到 cutter 上：
  讓切點永遠跟著交點跑是另一個主張，使用者想要時可以用「點在物件上」講。

  ### 又一個被抽出來的重複

  圓的切點沒辦法走 `TrimCutsAlongArc` —— 整圈會 wrap 成 sweep = 0，
  而那個函式（正確地）拒絕除以它。
  所以把「cutter 和這個圓在哪裡相交」抽成 `CircleHits`，兩邊共用；
  line-circle 和 circle-circle 的數學沒有第二份。

- **ADR-M17-047** — **Transform**：移動、旋轉、縮放，可選擇留下複本。

  一個按鈕、一個對話框（模式 + 數字 + 「留下複本」），
  而不是四個按鈕 —— 工具列已經 46 個了。
  對話框只顯示**當下模式用得到的那一列**：三個數字框裡有兩個沒人讀，
  等於邀請使用者填一個不會被讀的值。

  ### 原地移動：不加也不減任何約束

  移動就是改座標。草圖的約束**仍然是關於這個形狀的事實**，
  接下來那次求解**有權**把東西拉回原處。
  那不是指令失敗 —— 那是草圖在說「它本來就被釘住了」。

  所以這裡刻意**不**發明一個約束去固定新位置。
  發明一個，等於替使用者回答一個他沒問的問題。

  ### 複本：內部的約束帶走，向外的留下

  | 約束 | 處置 |
  |---|---|
  | 只牽涉選取範圍**內部**的 | **複製**到複本上 |
  | 伸到**外面**的 | **不複製，但計數並回報** |

  複製向外的約束會把複本綁在**原件的鄰居**上 ——
  從牆上複製一個矩形，複本還黏在那面牆上。

  而這裡「丟掉」是誠實的，Split 裡卻不是：
  **原件保留了每一個約束**，使用者打的東西一個都沒少。
  Split 是把原件**換掉**，所以丟掉就是真的丟掉。

  ### 複製的尺寸拿到**自己的** Parameter

  共用原件的 Parameter 看起來對，然後會拒絕讓複本改尺寸 ——
  那是使用者沒要求、而且**看不見**的關聯。
  Offset 早就是自己開一個 Parameter，這裡跟著它，數值照抄。

  ### 錨點

  旋轉和縮放需要一個中心。規則：
  **選取範圍裡剛好有一個「點」圖元時就用它**（那是使用者在指定位置），
  否則用選取範圍的中心。**用了哪一個會寫在狀態列**，
  因為兩者結果差很多，而無聲的選擇會看起來像指令壞掉。

  弧的範圍用它**自己的**起點／終點／中點，不是它所屬圓的外框：
  一段位在大圓頂端的短弧，離那個圓的外框中心很遠。

  ### 一個我自己犯的錯，值得留著

  第一版的複製迴圈**一邊走 `sketch->constraints()` 一邊往裡面加約束** ——
  在被追加的 vector 上迭代。它複製了 8 個裡的 2 個，然後**回報成功**。

  那正是這個專案一直在寫測試防的形狀：
  **一個看起來合理的數字、沒有錯誤訊息、而幾何會在下一次拖曳時散掉。**
  測試斷言的是「8」而不是「有複製到東西」，所以它當場紅了。

  現在兩個分支都是**先全部讀完，再全部寫**，
  並且在註解裡寫明 `sketch` 是指進 document 的指標、每一次寫入都是對它的寫入。

  ### 拒絕

  - 移動距離 0 / 縮放 1：原地是包著成功訊息的 no-op；
    複製則是把複本疊在原件正上方，唯一能發現的方法是注意到 DOF 變高了。
  - **負的縮放是鏡射，而鏡射已經有了** —— 直接說，而不是照做。

- **ADR-M17-048** — **橢圓與橢圓弧**：求解器、序列化、profile、kernel 四邊同時長。

  ### 一、為什麼是**新的型別**，不是圓多兩個欄位

  最順手的做法是給 `SketchCircle` 加上第二個半徑和一個旋轉，
  圓就是「兩個半徑相等」的那一種。**那是錯的做法。**

  這個專案有 **143 個**地方讀 `SketchGeometry` 的分支。
  加欄位的話，每一個讀 `circle.radiusMm` 的地方都會**照樣編譯**，
  然後開始默默地表示「長軸半徑」—— 正是這個程式庫存在的意義所在的那種無聲錯誤。

  在 variant 裡加新的 alternative，會**打斷窮舉的 visit**，
  由編譯器點名每一個必須做決定的地方。第一次編譯就抓到三個 static_assert
  和幾十個欄位錯誤。

  ### 二、參數不是角度

  ```
  point(t) = centre + R(rotation) · (major·cos t, minor·sin t)
  ```

  **t 不是從圓心到那一點的角度**，除非它剛好是圓。
  把 `atan2(p − centre)` 寫進去，在**四個軸點上是對的**、在其他每一處都是錯的 ——
  這正是那種能撐過隨手測試的錯誤。

  所以：`PointOnEllipse` 是唯一把參數變成點的地方，
  `EllipseParamOf` 是唯一的反向（先把兩軸「拉直」成單位圓，再取 atan2），
  序列化的欄位叫 `startParamRad` 而不是 `startAngleRad`，
  而 OCCT 的 `gp_Elips` 用的正好是**同一個參數化**，所以 trim 時一個轉換都不需要。

  ### 三、`get_if` 鏈裡的三顆地雷

  編譯器抓不到 `std::get<SketchArc>(geometry)` 當成「剩下只可能是弧」的收尾。
  variant 一長大，那三行就變成 **bad_variant_access**：

  | 位置 | 什麼時候炸 |
  |---|---|
  | `DragTargetOf` | 拖任何一個橢圓 |
  | `SameSketchGeometryValue` | 拖曳的 undo 記錄 |
  | `SameSketchGeometry`（求解器 commit 路徑） | **每一次**含橢圓的求解 |
  | `TransformedGeometry`、`TransformAnchor` | Transform 選到橢圓（我今天才寫的） |

  全部改成窮舉的 visit 或帶 `static_assert` 的收尾。

  ### 四、一連串**無聲的拒絕**，以及它們怎麼被抓到的

  「點約束在橢圓上」一開始不收斂。追下去發現的不是求解器的數值問題，
  而是**旋轉的尺寸標註根本沒有生效**，所以橢圓一直可以自由轉，
  把系統變成一個又長又淺的山谷。而它沒生效的原因有兩層，兩層都是無聲的：

  1. `UnitMatches` 只認得 `AngleConstraint` 是弧度的 —— 其他一律要 mm。
     新的旋轉約束綁的是弧度參數，被判「單位不相容」而拒絕。
  2. 修好之後還是不動：`DimensionValueValid` 要求非角度的值 ≥ 1e-6，
     而一個長軸沿著 +u 的橢圓，旋轉**正好是 0**。

  兩者都不會出現在使用者面前 —— 草圖只是多報一個自由度。

  ### 五、順手修好的三個求解器缺陷

  1. **阻尼是絕對值**：`1e-6` 加到 J'J 的對角線上。
     那個數字本身沒有意義 —— 對以微米計的問題是重阻尼，對以公尺計的等於沒有。
     更糟的是它**長不大**：欠約束的草圖依構造就是秩虧的，
     LDLT 會沿著零空間丟回任意大的步長，要壓住它需要和 J'J 同量級的阻尼，
     而從衰減到 1e-12 的值開始、十二次乘十倍，永遠到不了。
     改成 **J'J 對角線最大值的比例**，並把嘗試次數提高到 24。
  2. **迭代次數每輪加兩次**：迴圈頭一次、迴圈尾一次。
     三輪的求解回報六次，而「上限 100」其實是 50。
  3. **點在橢圓上的 residual**：從隱式的
     `(x/a)² + (y/b)² − 1` 改成**徑向距離** `d − d/reach` ——
     從圓心射出的那條射線上，點離橢圓有多遠，單位是毫米。
     隱式版離曲線遠時以**平方**成長，梯度巨大、曲率主導每一步。

  修完之後，六個測試起點（含正中心附近、含遠處）**全部在 3–7 次迭代內收斂**。

  ### 六、誠實的拒絕

  - **半徑／直徑標註**：橢圓有兩個半徑，會**驅動長軸**而不說一聲。
    拒絕，並指名該用哪個指令。
  - **Trim / Split**：找出某物和橢圓的交點是四次方程式，EP3D 沒有。
    直說，而不是用畫布取樣器猜一個差一點點的位置。
  - **Offset**：離橢圓固定距離的曲線**不是橢圓**（是八次的偏置曲線）。
  - **Mirror**：反射本身很簡單，但這個專案的鏡射會**綁住**複本 ——
    而兩個橢圓之間沒有可以綁形狀的相等約束。位置跟著動、形狀慢慢飄，比沒有這個指令更糟。

  ### 七、順手翻掉的一條舊規則

  `M12_SNAP_006` 和 `M17_HANDLE_002` 釘著「弧的兩端不是點」，
  理由是「求解器沒有對應的變數」。**那個理由在 ADR-M17-018 之後就不成立了** ——
  圓角的接點、槽孔的角落、相切弧的接續，全都建立在弧端點是真變數之上。
  沒跟上的是**吸附器**：使用者沒辦法點一個弧的端點來從那裡開始畫東西，
  而那正是上面所有幾何存在的目的。現在弧和橢圓弧都提供圓心和兩個端點。

  ### 八、smoke test 抓到的兩件事

  1. 「主軸標註」和「橢圓工具」共用了同一個圖示 ——
     `--selftest` 直接說「兩個按鈕帶著相同的圖示」。
  2. 相切求解變好之後，圓被移到了正確的位置，
     而 selftest 硬寫的點擊座標 `(40,30)` 就不在圓周上了 ——
     **一個因為程式開始正常運作而失敗的測試**。
     改成去問圓現在在哪裡，並且順便**檢查相切真的成立**（原本只檢查它出現在清單裡）。

  - **相切**：線和橢圓、橢圓和其他曲線。需要在橢圓上解出接觸點。
  - **Trim / Split / Offset / Mirror**：見上，各自有各自的理由。

- **ADR-M17-049** — **雲形線**（內插式），以及第一個「變數個數不由型別決定」的圖元。

  ### 一、通過點，不是控制點

  `SketchSpline { std::vector<Vec2> points; bool closed; }` ——
  點在曲線**上**，那是使用者點哪裡就過哪裡的那一種。
  控制點式是同一組數字的**另一種讀法**，
  用一個旗標決定要怎麼讀，正是這個專案一直在付代價的那種無聲重新詮釋，所以還沒有。

  ### 二、`EntitySlots` 的假設被打破了

  這是**第一個變數個數不是型別屬性**的圖元。
  七個點的雲形線有十四個變數，三個點的有六個 ——
  所以 `EntitySlots` 長出一個 vector，而不是第八、第九、第十個欄位。

  跟著要處理的是**寫回**：其他每一種都是按 sub-element 分流的，
  而雲形線的**內部點全部帶著 `Whole`** ——
  照樣分流的話，每一個內部點都會蓋到同一組欄位，
  於是「移動最後一點」會把中間整個改寫。所以雲形線是**按位置**收集的。

  這個突變（把分流改回 sub-element）被 SPL_007 和 SPL_008 抓到。

  ### 三、只有兩端可以被約束

  `SketchElementRef` 是「entity + sub-element」，而 sub-element 只有四種 ——
  **內部點沒有名字可以給約束用**。
  這是**參考的限制，不是求解器的**：每一個點都是變數，求解器全都會動。

  這件事是**說出來**的，不是繞過去：把雲形線的端點接到鄰居上正是 profile 需要的，
  而那個是能用的。封閉的雲形線則像圓一樣**完全沒有端點**。

  DOF 老實報數：n 個點就是 2n。

  ### 四、Core 取樣 vs kernel 曲線 —— 一個**有界的**接縫

  Core 用 Catmull-Rom（局部的：拖一個點只改變它兩側的兩段，那是使用者預期的），
  kernel 用 OCCT 的 `GeomAPI_Interpolate`（而不是 `PointsToBSpline` ——
  前者**穿過**每一點，後者只是**靠近**，
  而一條端點只是「大約」在鄰邊端點上的曲線是**封不起來**的）。

  兩者**在每一個給定點上完全一致**，中間差一個弦長的零頭。
  這個差別是真的，而且是有界的：**取樣決定繪製、拾取、和哪個 loop 包住哪個**，
  **kernel 決定實體**；而必須完全一致的地方（profile 串接的端點）是完全一致的。

  Core 這一側只有**一個**取樣器，畫布、拾取、profile 的繞繞數測試共用它 ——
  畫一條比較漂亮的曲線，等於畫一條程式其他部分不相信的曲線。

  ### 五、一顆真的爆掉的地雷

  `SPL_007` 直接讓測試程序**以 exit 3 死掉**，沒有任何訊息。

  `SketchSolveSession` 的 `SameSketchGeometry` 是一條 `get_if` 鏈，
  以 `std::get<SketchArc>(a)` 收尾（「剩下只能是弧」）。
  M17.25 我修過 `PartDocument` 裡那一份，**漏了這一份** ——
  於是雲形線一出現，它就在一個 `noexcept` 函式裡丟出 `bad_variant_access`，
  而那個函式在**每一次求解的 commit 路徑上**。

  修法不是補第三個分支，而是**把兩份合成一份**：
  `SameSketchGeometryValue` 移進 Core，窮舉、帶 `static_assert`，兩邊都呼叫它。
  下一個 alternative 會讓**編譯失敗**，而不是讓程序死掉。

  ### 六、誠實的拒絕

  Trim（縮短一條雲形線等於移動它通過的點，而哪些點該動不是一次點擊說得出來的）、
  Split（切出來的兩段會是「通過沒人點過的點」的雲形線）、
  Mirror 和 Offset（同橢圓：綁不住形狀／偏置曲線不是雲形線）。

  ### 七、一個**沒有**斷言的東西，以及為什麼

  `M17_KERNEL_041` 用四個對稱的點做封閉雲形線，每一段弦等長。
  照理質心應該在原點。**OCCT 給的是 x 差 2.6 mm**（40 mm 的形狀上），
  遠大於質量積分的誤差（橢圓面約 1e-3 mm）。
  週期參數化從哪一點開始，似乎會破壞對稱性。

  那是一個真的問題，而這裡**沒有回答它** ——
  所以測試只斷言體積被夾在「四點菱形」和「外接盒」之間（那正好分辨內插與擬合），
  以及質心在形狀內部。
  **斷言對稱等於斷言一個信念，而不是一個量測。**

- **ADR-M17-050** — **一個範例檔，和它第一次執行就找到的 bug。**

  `examples/spline-and-ellipse.ep3d`，由 `tools/MakeExampleEp3d.cpp`
  透過**一般的 document API** 產生 —— 不是手寫 JSON。
  手寫的範例是這個格式的第二份定義：一開始一致，然後就不一致了。

  產生器會**寫檔、立刻讀回來、重新求解**。
  一個打不開的範例不是任何東西的範例。

  ### 它找到的東西

  第一次執行，橢圓在存檔前 DOF 0，讀回來之後**拒絕求解**：

  ```
  constraint 11: a dimensional constraint is not bound to any Parameter
  ```

  序列化的**寫入端**是泛用的（`BoundParameterId` 走那一份清單）。
  **讀取端**卻是每一種約束各自手寫一行 `c.parameterId = parameterRef();` ——
  **八份拷貝**。M17.25 加了兩個尺寸約束，兩份都沒寫。

  它們**存檔完全正確**（寫入端是泛用的），回來時綁在空的上面。
  這是這個專案的招牌缺陷再一次：
  **兩個必須一致的東西，中間一份手抄，而各自的測試都不會發現不一致。**

  讀取端現在也是泛用的：`IsDimensional` + `VisitBoundParameter`，同一份清單反過來讀。

  `M17_SER_043` 用**能力**釘住它 —— 走過每一個 `IsDimensional` 為真的約束，
  而不是走一份測試自己也要記得擴充的清單。
  把那個泛用區塊關掉，**8 個測試變紅**。

  ### 為什麼一個範例檔會比測試先找到它

  1400 多個測試裡沒有一個把「一個帶橢圓尺寸的文件」**存檔後再求解**。
  序列化測試檢查欄位回得來（`parameterId` 確實在檔案裡），
  求解測試在記憶體裡建構文件。**沒有人走完整條路。**

  一個範例檔天生就會走完整條路 —— 那就是它的用途。

- **ADR-M17-051** — **`ep3d`：無頭的命令列腳本模式。**

  ```
  ep3d --script part.ep3ds [--open in.ep3d] [--out out.ep3d] [--quiet]
  ```

  ### 一、為什麼是**另一個執行檔**，不是 viewer 加一個旗標

  viewer 在讀 argv **之前**就建好了 `QApplication`。
  所以任何「無頭」的執行，其實都是一個剛好沒開窗的 GUI 行程 ——
  那和「可以在 CI 裡、在容器裡、透過 ssh 跑的工具」是兩件事。

  `ParametricCADViewerCore` **本來就沒有 Qt**（它是草圖的模型和指令，不是 widget），
  所以直譯器和 `ep3d` 直接連它，整個 binary 完全不需要 Qt。

  ### 二、它走的是**滑鼠那條路**

  `tool` / `click` 驅動 `SketchCanvasModel`，`click` 還會經過**真正的吸附器** ——
  所以點在既有幾何上會推論出和滑鼠一樣的重合約束。
  `constrain` / `dimension` 走 `requestConstraint` / `requestDimension`，
  也就是**決定一個選取到底有沒有意義**的那兩個函式。

  如果腳本直接組 constraint struct，那會是**進入模型的第二條路** ——
  而第二條路永遠是那條「還能動、但第一條已經壞了」的路。

  ### 三、詞彙表只有一份

  工具名、約束名、尺寸名各只有一張表，那張表**同時是**解析器、`--help` 的內容、
  和錯誤訊息裡的「已知有這些」。
  一個詞彙抄三份（一份解析、一份印、一份解釋）正是這個專案的招牌缺陷。

  `M17_CLI_001` 用 **enum 的範圍**（而不是一份測試也要記得擴充的清單）
  數 `SketchTool`，少一個就紅。突變測試拿掉 `slot` → 紅。

  ### 四、它第一次跑就找到一個 bug

  `constrain concentric Ellipse1 Circle1` 被拒絕，訊息是
  「Ellipse #5 不是圓也不是弧」。

  `requestConstraint(AddConcentric)` 問的是 `IsCurveRef`，
  而 `IsCurveRef` **刻意排除橢圓**（因為它其他每一個呼叫者都要「一個半徑」）。
  結果這個指令拒絕了一個**求解器從 M17.25 就支援的約束** ——
  而且訊息說的理由是真的、但不是原因。

  修法是把概念命名一次：`IsCentredRef`（圓、弧、橢圓、橢圓弧），
  和求解器自己的 `centredSlots` **接受的是同一個集合**。

  這個 bug 在 GUI 裡一樣存在：選一個橢圓和一個圓、按 Concentric，一樣被拒絕。
  **沒有任何測試碰過它**，因為沒有測試把「橢圓 + Concentric」這個組合按過一次。

  ### 五、失敗要**停下來**，而且要說第幾行

  一個繼續往下跑的腳本會蓋出作者沒寫的東西，
  而意外會在好幾個指令之後才出現，且沒有東西指向原因。

  CTest 註冊了兩個測試：跑真正的範例腳本，
  以及一個 `WILL_FAIL` 的壞腳本 —— **一個對失敗回傳 0 的 CLI，會讓每一次綠燈都失去意義。**

- **ADR-M17-052** — **一個 socket，直接控制執行中的 viewer。**

  ```
  ParametricCADViewer --listen [PORT]     # 預設 5310，印出實際的 port
  ep3d --connect [PORT] --script part.ep3ds
  ep3d --connect [PORT]                   # 從 stdin 讀，當成主控台用
  ```

  指令送過去，**幾何就出現在那個開著的視窗裡** ——
  那是「產生一個檔案」和「使用這個程式」的差別。

  ### 一、只綁 loopback，而且**沒有旗標可以放寬**

  這條路會執行**建立、修改、以及儲存檔案**的指令。
  綁在任何搆得到的位址上，它就是一個**沒有驗證的遠端指令服務** ——
  那不是可以當作「方便功能」出貨的東西。

  `QHostAddress::LocalHost` 只出現在一個呼叫點，`ScriptServer` 裡沒有第二個分支。
  真的要跨機器的人可以自己做 port forwarding ——
  那是一個**知道自己在做什麼的人**做的決定。

  ### 二、Session 是原始操作，`RunSketchScript` 是它上面的一行

  檔案把所有東西一次交給一個呼叫。**socket 不是**：
  `tool line` 來一則訊息，`click 0 0` 另一則，`click 100 0` 又一則。
  每次都從頭開始的直譯器，會對每一個連線的第二行回答「還沒有草圖」。

  所以 `SketchScriptSession` 是原始操作，而 `RunSketchScript` 是
  「開一個 session、跑一次」。
  兩個直譯器（一個給檔案、一個給連線）就是同一份詞彙抄兩次。

  **一個連線一個 session**：當前草圖、當前工具、目前給過的名字，
  屬於那段對話而不是那個行程 —— 否則兩個 client 會互相把對方的雲形線畫完。

  ### 三、TCP 是**串流**，不是訊息

  一個指令可能分兩個封包到，兩個指令可能擠在一個封包裡。
  拿「緩衝區裡剛好有的東西」去跑，會執行半行。

  所以 `readFrom` 只跑**完整的行**。
  `--selftest` 用**真的 socket**測這件事：一次寫兩個指令、以及把一個指令拆成兩次寫。
  突變測試（拿掉分行）→ **4 個 selftest 檢查同時紅**。

  ### 四、行號的格式化交給**傳輸層**

  第一版的直譯器把 `line N: ` 印進訊息裡。
  結果 socket 每一則回覆都是 `line 1:`（每則訊息都是自己的一次呼叫，所以每行都是第 1 行）——
  而唯一的修法會是**傳輸層用字串手術把它拆掉**，也就是傳輸層知道直譯器的標點符號。

  改成 `ScriptLogEntry { int line; std::string text; }`：
  檔案那端印 `line 12: tool circle`，連線那端印 `tool circle`。

  ### 五、`help` 是一個**指令**

  socket 上沒有 `--help` 可以跑。而它問的是**同樣那三張表** ——
  和 CLI 的 help、和錯誤訊息裡的「已知有這些」是同一份。

  ### 六、client 也不用 Qt

  `ep3d` 刻意不依賴 Qt（才能在 CI、容器、ssh 上跑），
  所以 client 用的是原生 socket（Windows 上 winsock2，其他地方 BSD sockets）——
  為了一個「送幾行、讀幾行」的 client 把 Qt 拉進來，會把它唯一有用的性質毀掉。

  ### 七、`--listen 0`

  作業系統挑一個沒被佔用的 port，程式**印出它實際拿到的那個**。
  自我測試就是這樣綁的 —— 寫死一個號碼會在某台剛好在用它的機器上失敗，
  那是 flake，不是發現。

- **ADR-M17-053** — **顏色是每個圖元自己的事**，不是整張草圖的。

  ### 一、使用者第一眼就看出來了

  「你畫的那條 spline，沒有被約束、不是黑色的。」

  約束**確實在那裡** —— 兩個 Coincident 直接指名那條雲形線。
  問題在畫布：

  ```cpp
  const QColor geometryColour = GeometryColour(target->solveStatus());
  ```

  **顏色來自整張草圖的狀態。** 草圖是 UnderConstrained（DOF 10，
  雲形線中間那五個點），所以**裡面每一樣東西**都被畫成鬆的 ——
  包括那條**已經被完全釘死**的弦線。那一半單純是錯的。

  而且比一行錯更糟：**只要草圖裡有一條雲形線，它就永遠不可能變黑** ——
  沒有任何約束叫得出內部點的名字，所以它一定留著自由度。
  雲形線一進到產品裡，顏色這個通道對任何含有雲形線的草圖就不再帶訊息了。

  ### 二、「哪些變數是自由的」是求解器已經在回答的問題，只是問法不同

  DOF 說**還剩幾個**自由度；這裡要問的是**是哪幾個**。

  一個變數是自由的，**恰好**當 Jacobian 在解上的零空間有沿著它的分量 ——
  而那種方向的數量**就是**秩所量的零化度。
  所以「有幾個」和「是哪些」不可能給出互相矛盾的答案。

  用 SVD 而不是秩用的那個 QR：秩只需要一個數目，這裡需要零空間本身。
  兩者用**同一個相對門檻**、算**同一個矩陣**。

  門檻下在 V 的**那一欄**上，不是只看奇異值：
  在某個零方向上只有極小分量的變數不算真的自由，而捨入誤差幾乎到處都放一點分量。

  ### 三、失敗的求解**什麼都不知道**

  沒解過、或解失敗的草圖，`isEntityFullyConstrained` 一律回 false。
  **這是安全的方向**：「不知道有沒有被釘住」讀起來就是鬆的，
  而回 true 等於宣稱一個沒有人做過的量測。

  同樣的理由，每一條讓求解狀態失效的路徑都會清掉那個集合 ——
  留著舊答案，會用編輯前的量測把編輯後的圖元漆成黑色。

  ### 四、整張草圖的顏色還留著一個用途

  **麻煩**：衝突、或無效的約束。
  那是整組方程式的性質，沒有誠實的方法說是哪一個圖元的錯，
  所以那種狀態下畫布仍然整張一個顏色。

  ### 五、突變測試

  把「有沒有分量」永遠當成沒有（於是每個圖元都變成已釘住）→ **3 個測試紅**。

- **ADR-M17-054** — **雲形線的每一個點都叫得出名字**。

  ### 一、原本的缺口

  `SketchElementRef` 只認得四種子元素：`Whole`、`StartPoint`、`EndPoint`、
  `CenterPoint`。雲形線中間的點一個都不在裡面。

  求解器其實一直都把每個點當成兩個變數在解，畫布也一直把它們畫出來 ——
  **但沒有任何一條約束叫得到它們**。七個節點的雲形線有 14 個自由度，其中
  10 個是整個程式碼裡沒有任何一條路徑可以碰到的。

  結果是：**七節點的雲形線永遠不可能完全約束**，所以 ADR-M17-053 剛做好的
  「完全約束就變黑」，在雲形線上永遠不會發生。使用者反映的「不是黑色」，
  真正的原因在這裡，不在顏色。

  ### 二、決定

  加上第五種子元素 `SplinePoint`，並在 `SketchElementRef` 上加一個 `index`。

  ```cpp
  enum class SketchSubElement { Whole, StartPoint, EndPoint, CenterPoint, SplinePoint };
  struct SketchElementRef {
      SketchEntityId entityId{kInvalidSketchEntityId};
      SketchSubElement subElement{SketchSubElement::Whole};
      int index{0};   // 只有 SplinePoint 用得到
  };
  ```

  ### 三、一個點，一種寫法

  這是這個 ADR 真正的規則，其他都是它的推論。

  第 0 個點就是 `StartPoint`，最後一個點就是 `EndPoint`。**`SplinePoint` 只
  用來指中間的點**，指到頭尾一律拒絕。

  如果兩種寫法都成立，同一個點就會跟自己比較起來不相等：
  - 在畫布上點它兩次會像是選到兩個不同的點；
  - 在兩種寫法之間下一個 `Coincident`，會是一條什麼都沒約束、卻照樣吃掉一個
    自由度的約束 —— 於是 DOF 永遠差 2，而畫面上完全看不出哪裡不對。

  封閉的雲形線沒有頭也沒有尾（就像圓沒有），所以它的**每一個**點都用
  index 指。

  這條規則寫在**一個地方**：

  - `IsResolvableRef()`（Core）判斷一個 ref 解不解得開；
  - `SplineRefFor()`（畫布）是「第 i 個點」轉成 ref 的**唯一**入口 ——
    選取、控制點、腳本剖析器全部走它。

  抄成兩份的話，遲早會抄得不一樣，而那正是這個專案一再出現的那種缺陷。

  ### 四、順帶收掉的兩個 switch

  編譯器沒有逼我去看的兩個地方：

  - `SurvivesSplit()`：切開雲形線會把點重新編號 —— 原本的第 4 點會變成第二段
    的第 1 點，或者根本消失。所以指到雲形線點的約束**不能**存活，一律
    `Refuse`。今天切雲形線本來就被 `PlanSplit` 擋掉，這是為了將來拿掉那個
    限制的時候，不會有人的約束被默默搬到別的點上。
  - `SketchReconstructor` 的 `pointFor()`：原本用 `default: return nullopt`，
    對之後新增的每一種子元素都回答「沒有這個點」—— 而那個回答會讓一次驗證
    默默地通過。改成走 `PointOfSubElement()` 這個唯一的查詢。

  ### 五、檔案格式

  `index` **只在 `SplinePoint` 的時候寫出來**。所以 M17.30 之前寫的每一個
  檔案，重存之後仍然逐位元組相同 —— 一個到處都寫的欄位，會讓磁碟上每份文件
  第一次重存就整份變動，diff 就再也看不出使用者到底改了什麼。

  讀回來的時候：欄位不在就是 0（那正是舊檔的意思），欄位在但不是一個整數點號
  就**拒絕**。四捨五入成 2 會把約束放到沒有人選的點上。

  ### 六、腳本語彙

  `Spline1.p3`。`p0` 允許打（那是最直覺的寫法），但它解出來的是
  `.start` 那個 ref，不是第二種寫法。超出範圍的拒絕訊息會把範圍講出來
  （「有 3 個點，編號 0 到 2」），因為那個數字正是寫的人弄錯、而且從腳本上
  看不出來的東西。

  ### 七、突變測試

  | 突變 | 結果 |
  |---|---|
  | `SplineRefFor` 忘記最後一個點是端點 | **2 紅**（M17_CLI_025） |
  | `IsResolvableRef` 讓端點多一種寫法 | **2 紅**（M17_SPL_012） |
  | `SlotFor` 不看 index，永遠取第 0 點 | **10 紅** |
  | 序列化器對每一種子元素都寫 index | **2 紅**（M17_SER_046） |

  第一個突變**第一輪是活的** —— 當時沒有任何測試檢查「最後一個點」這條分支，
  只檢查了第一個。那條分支跟第一條是兩行不同的程式碼，而只看第一行的測試就
  只守得住第一行。M17_CLI_025 是為了殺掉它才補的。

  ### 八、還沒有的

  - 兩個點之間的**弧長**、雲形線的**曲率**或**端點切線方向**都還不能約束。
    能約束的是每個點的位置，這已經足以把整條線釘死（14 個變數，14 條約束，
    DOF 0），但不是 Onshape 對雲形線能做的全部。

# M18 — 草圖收尾與量測

## ADR-M18-001 — 雲形線端點的切向就是**弦**，而且精確

### 一、原本的缺口

`Tangent` 直接拒絕雲形線。所以雲形線**不能跟任何別的圖元乾淨地接起來** ——
畫得再準，接縫處都有一個看得見的折角。這是它進不了任何輪廓的直接原因，
而掃掠與放樣要的就是輪廓。

### 二、關鍵發現：弦就是切向

Core 把雲形線當成**均勻 Catmull-Rom，兩端反射**（`SplinePointAt`）。
反射點是 `2*p0 - p1`，代進 Catmull-Rom 在 u=0 的導數 `0.5*(c - a)`：

```text
0.5 * (p1 - (2*p0 - p1)) = p1 - p0
```

尾端同理是 `p[n-1] - p[n-2]`。

所以「這條雲形線從端點往哪個方向離開」是一個**只跟兩個點有關**的問題，
而那兩個點都已經是求解器的變數。這不是近似，是恆等式。

### 三、後果：不需要新的殘差

| 相切對象 | 用的方程式 | 為什麼是它 |
|---|---|---|
| 線 | `LinesParallel`（弦 vs 線） | 「同方向離開」就是「兩線平行」 |
| 圓／弧 | `TangentAtPoint`（弦 ⊥ 半徑） | 觸點已被 PointOnObject 釘住，距離式會停在極值上（ADR-M17-044） |
| 另一條雲形線 | `LinesParallel`（兩條弦） | 同上 |

**零個新殘差種類。** 再寫一份說同樣事情的殘差，就是多一對必須保持一致的東西。

### 四、Kernel 也要知道

這是本 ADR 真正重要的部分。

`GeomAPI_Interpolate` 如果不給端點切向，會自己挑端點條件 —— 而那**不是弦**。
所以在 M18 之前，使用者在草圖上約束的相切，做出來的實體上並不成立：
草圖說「平滑」，實體有折角，而程式裡沒有任何東西看得出來。

修法是把弦當成端點切向交給 OCCT（`Load(initial, final, Scale=true)` ——
保方向，長度讓 OCCT 決定，因為弦長只是鄰點恰好落在哪裡的產物）。

**而這暴露出一個既有的接縫**：內插被寫了兩份 —— 一份建實體的 profile 邊，
一份建 3D 視圖畫的線框。兩份分別寫的 `GeomAPI_Interpolate`。
其中一份學會端點切向而另一份沒有的那一刻，**預覽和實體會是通過同樣的點的
兩條不同曲線**。合併成 `InterpolateSplineThrough()` 一份。

`SplineEndDirectionsOf()` 是為了測試而開的**核心中立的門**，理由跟 `BoundsOf`
一樣（ADR-M4-004）：「弦就是切向」這個主張橫跨 Core 的求值器和 OCCT 的內插器，
沒有一扇能問第二邊的門，程式裡就沒有任何東西能檢查兩邊還是不是一致的。

### 五、拒絕的部分

- **整條雲形線相切**：雲形線每個點的切向都不同，「這條線跟那條線相切」不構成
  一個方程式。要說是哪一端。
- **封閉雲形線**：沒有端點，就像圓沒有。
- **雲形線排第二**：`at` 在這個約束裡到處都是指 `a` 的端點，讓端點屬於另一個
  entity 會默默把它套到線上 —— 釘住一個沒有人選的點。

### 六、突變測試

| 突變 | 結果 |
|---|---|
| 尾端的弦取錯鄰點 | 第一輪**活的** → 補 M18_TAN_009 後 2 紅 |
| 不告訴 kernel 端點切向 | 2 紅（M18_KERNEL_001） |
| 雲形線對圓用平行式 | 2 紅（M18_TAN_003） |

第一個突變活下來，是因為當時所有測試用的都是**三點**雲形線 ——
而三點的時候起點的鄰點（index 1）和終點的鄰點（index count-2）**是同一個點**。
四點是兩者第一次不同的地方，M18_TAN_009 就是為此存在。

## ADR-M18-002 — 線與橢圓相切有閉式解，其他的沒有

### 一、方程式

在橢圓自己的座標系裡，單位法向 `(nu, nv)` 的直線與它相切，
當且僅當它到中心的帶號距離 `h` 滿足

```text
h^2 = a^2 nu^2 + b^2 nv^2
```

右邊是「法向為 n 的切線離中心多遠」。**式子裡沒有觸點** ——
這正是線是唯一有閉式解的相切對象的原因。

### 二、為什麼是平方式，不是 `|h| - R`

絕對值在 `h = 0`（線穿過中心）有一個角點，導數在那裡變號 ——
拖過中間會讓線跳到另一邊。平方式處處平滑，而且在解上 `h = ±R ≠ 0`，
導數是 `2h`，所以不是 ADR-M17-044 那種秩不足的情況。

除以 `(a² + b²)` 化成無因次，跟這裡每一條正規化殘差一樣：
一個容差要同時服務 1 mm 的橢圓和 100 mm 的橢圓。

### 三、拒絕的部分

圓、弧、雲形線、第二個橢圓 —— 都需要把**觸點參數**解出來，
而目前沒有任何約束擁有自己的變數。

拒絕並說出缺什麼，不做近似。這裡的近似會是一個**收斂了但沒碰到**的相切，
也就是 ADR-M17-044 那個失敗換一扇門進來。

### 四、突變測試

| 突變 | 結果 |
|---|---|
| 殘差忽略旋轉 | 6 紅 |
| 殘差把兩個半軸對調 | 8 紅 |

## ADR-M18-003 — 雲形線可以鏡射了（而拒絕的理由曾經過期）

`ApplyMirror` 拒絕雲形線，理由是「只有兩端叫得出名字，所以複本的中間綁不住原件」。
**M17.30 之後這句話就不成立了**，但拒絕留在原地。

一個**活得比它的理由久的拒絕**，是在跟使用者說一件關於他自己程式的假話 ——
比缺功能更糟。

反射每個點，順序不變。這是精確的：Catmull-Rom 是點的加權和而權重和為 1，
所以「先反射再內插」等於「先內插再反射」。弧必須交換兩端（它的方向存成一對角度），
雲形線的方向就是點的順序，同順序的鏡像就是反射本身。

每個點一條 `Symmetric`：複本每點兩個自由度，每條對稱兩個方程式，恰好定數。
**沒有 `Equal`** —— 圓需要一條來鎖半徑，雲形線除了點在哪裡以外沒有尺寸。

橢圓仍然拒絕，理由未變且仍然成立：鏡射在這個專案裡是**綁住**複本，
而兩個橢圓之間沒有可以綁形狀的相等關係。

## ADR-M18-004 — 量測是查詢，不是文件物件

roadmap §33.1 自己說 §50（量測）該提前，理由是**每一次使用者驗證目前都靠人工算體積**。
一個測試讀得到的數字，是「宣稱過的驗證」和「量過的驗證」之間的差別 ——
而這個價值花在它之後的每一個 milestone 上，不是花在它落地的那一個。

### 一、查詢，不是標註

沒有 ObjectId，不進 document，不可復原。這就是它跟**從動尺寸**的差別
（roadmap 50.3.4）：從動尺寸是一個剛好唯讀的持久標註，量測是「看」。

### 二、單位不能說謊

`UnitType` 沒有面積 —— 它是用來標記 Parameter 的，而這個程式裡沒有任何參數
是面積。拿 `Millimeter` 頂替，30 mm 圓的面積印出來是 **`2827.4 mm`**：
一個看起來合理、但單位是錯的數字，比沒有數字更糟。

所以量測有自己的 `MeasureUnit`（mm、mm²、rad、無因次）。

### 三、近似要說出來

橢圓周長是橢圓積分，雲形線長度沒有閉式解。每個 `MeasureItem` 帶一個
`approximate` 旗標，CLI 印成 `(approx)`。
被告知「94.3 mm」而沒有別的訊號的讀者，會把它當成精確值用。

### 四、一個被第二種近似抓到的錯

橢圓周長原本是用 256 段弦去走。弦永遠切內角、從不超過，
所以誤差**同方向累積**而不互相抵消 —— 整圈 2π 只有 256 段，
精度只有十萬分之二，60×25 的橢圓上差 7 微米。

抓到它的是 M18_MEA_005 拿 **Ramanujan 第二近似**去比對 ——
一個**不同的**近似。拿取樣器跟它自己比什麼都證明不了。

改成對速度 `|dP/dt| = sqrt(a² sin²t + b² cos²t)` 做 Simpson 積分：
被積函數平滑且週期，誤差以步長四次方下降。

### 五、突變測試

| 突變 | 結果 |
|---|---|
| 面積報成 mm | 2 紅 |
| 取樣長度報成精確 | 3 紅 |
| 順時針弧反向量 | 1 紅 |
| Simpson 權重全部相同 | 1 紅 |
| 鏡射的雲形線只綁兩端 | 2 紅 |
| 鏡射不反射點 | 1 紅 |

### 六、還沒有的

- 兩個非點物件之間的**最小／最大距離**（roadmap 50.2 有列）
- 單位切換（cm / inch / degree）與精度切換
- 3D 的量測（實體、面、邊）—— 質量性質已經算得出來，但沒有接到使用者面前
