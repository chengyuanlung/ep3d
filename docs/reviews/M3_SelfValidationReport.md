### Inertia reference frame — previously unverified, now verified by execution

`OcctGeometryKernel.cpp` carries a comment asserting that
`GProp_GProps::MatrixOfInertia()` is already expressed about the centre of mass,
so no parallel-axis (Huyghens) shift is needed. Until this session that
assertion rested on documentation reading only — the file had never been
compiled, let alone executed.

It is now confirmed empirically, and the corner-origin convention is what makes
the confirmation meaningful: `M3_KERNEL_003` proves the COM sits at
(50, 25, 10) mm, i.e. **not** at the origin. An origin-relative inertia matrix
would therefore differ from the about-COM oracle by the parallel-axis terms
`m*d_com^2`, which for this box are of the same order as the diagonal terms
themselves — several orders of magnitude above the 1e-9 relative tolerance.
`M3_INERTIA_001` passing at that tolerance can only happen if the matrix is
already about the COM. No parallel-axis correction is required, and the comment
now describes a measured fact rather than an inference.

Tolerances are as documented in ADR-M3-002 and were not enlarged at any point;
the failures encountered during this session were fixed in production code, never
by relaxing a tolerance.

## Defects Found and Fixed During This Session

Both were latent in code that had been written but never compiled or executed on
the previous machine.

1. **`createBox` could never succeed** (`src/Kernel/Occt/OcctGeometryKernel.cpp`).
   `BRepPrimAPI_MakeBox`'s constructor only stores its parameters; `IsDone()`
   reports the `BRepBuilderAPI_Command` done-flag that only `Build()` sets
   ("Stores the solid in myShape" — `BRepPrimAPI_MakeBox.hxx`). The draft queried
   `IsDone()` without calling `Build()`, so every box construction returned
   `GeometryConstructionFailed`, and `Shape()` would have raised
   `StdFail_NotDone` had it been reached. This single root cause failed 16 of the
   21 OCCT tests on first execution. Fixed by calling `Build()` before
   `IsDone()`/`Shape()`; all 21 pass.
2. **Clean builds failed at the post-build test-discovery step** (`CMakeLists.txt`).
   `gtest_discover_tests`' default POST_BUILD mode runs the freshly linked
   executable to enumerate tests, but `ParametricCADKernelOcctTests` needs the
   OCCT DLLs that vcpkg's applocal step deploys in its own POST_BUILD command. On
   a clean build the enumeration ran first and the build failed with MSB3073.
   Incremental rebuilds masked it, because by then the DLLs were already in
   place — so it would have surfaced only on a fresh clone or CI. Fixed with
   `DISCOVERY_MODE PRE_TEST` on that target, verified by a from-empty rebuild.
   `ParametricCADCoreTests` keeps the default mode; it has no DLL-carrying
   dependency.

Additionally, `Standard_Failure` handlers were added around the OCCT calls in
both kernel methods. ADR-M3-001 and spec 7 state the interface never throws, but
the draft had no protection: OCCT signals internal errors by exception, and
without a handler one would have unwound out of the adapter and into Core,
breaking the documented contract at exactly the boundary M3 exists to defend.
Input validation still happens up front, so these handlers are a contract
backstop, not the primary failure path.

## Post-Review Fixes (revision 2)

The independent review returned **REQUEST CHANGES, 92/100** with five Major
findings and no Critical. All five are fixed; 13 regression tests were added in
`tests/M3ReviewFindingTests.cpp`, one or more per finding.

Each new test was verified to actually catch its defect: the fixes for Majors 1
and 2 were temporarily disabled and 4 of the 5 tests covering them failed
immediately, then passed again once restored. A regression test that cannot fail
is not evidence.

**Major 1 — stale mass properties reported themselves as current.**
`MassProperties::valid` was set true and never cleared, so after a geometry
failure the document still exposed `valid=1` with the previous numbers —
a direct violation of spec 2's "downstream current results do not falsely
succeed". Fixed at two levels: `PartDocument::refreshMassPropertiesCurrency()`
clears the flag whenever the mass node did not succeed in a pass, and the node's
own failure paths clear it too. The document-level half is the load-bearing one:
when the upstream box fails, the graph blocks the node with
`BlockedByDependency` and never invokes it, so no code inside the node could
have run. Retention is unchanged (ADR-M3-004) — the numbers survive, only their
claim to currency is withdrawn.

**Major 2 — `Feature::state()` claimed validity it could not have.**
`Feature::markDirty()` had no callers anywhere in `src/`. A restored feature read
`Valid` while holding no runtime shape (ComputeState is persisted, KernelShape
deliberately is not), and a feature kept reading `Valid` after a parameter edit
superseded its geometry. `PartDocument::syncFeatureStatesFromGraph()` now demotes
any cached `Valid` the graph disagrees with, called from the mutation, wiring and
recompute paths. Only false `Valid` is corrected, only ever downward to `Dirty`;
`Failed` is still reachable exclusively through a feature's own failed recompute.

**Major 3 — `removeObject` left a removed feature owned by its Body.**
It returned true and cleaned up graph and registry, but the feature stayed in
`Body::features()`: still serialized, still restored on load, and still the mass
node's source, so every later `recompute()` failed forever with "no box feature
configured". Added `Body::removeFeature`, and `removeObject` now handles the
`IRecomputable*` variant that a `BoxFeature` registers under — detaching the mass
node first, since it holds the id by value.

**Major 4 — save accepted documents that could never be loaded.**
Removing a Parameter still referenced by a BoxFeature produced a file that saved
cleanly and then failed to load forever, potentially over the only copy of the
data. The load path validated these references; the save path did not.
`validateSaveable()` now applies the symmetric check before writing, so the
dangling reference surfaces while the in-memory document is still repairable.

**Major 5 — wrong regression baseline in this report.** Corrected under
Regression above, with the per-file counts it should have carried originally.

**Minor also fixed:** `IsValidBoxDefinition` now rejects positive-but-degenerate
dimensions below `kMinBoxDimensionMm` (1e-6 mm) so they return a structured
`InvalidDimension` instead of an OCCT-internal throw; and OCCT exception
diagnostics fall back to the exception's type name when
`GetMessageString()` is empty, which it often is. (`typeid`, not OCCT's
`DynamicType()`: in OCCT 8.0.1 `Standard_Failure` derives from `std::exception`,
not `Standard_Transient`, so it has no `DynamicType()` — verified in
`Standard_Failure.hxx:28`.)

**Minor accepted, not fixed:** the reviewer noted that a public non-const
`PartDocument::massProperties()` lets any caller overwrite derived state.
Restricting it churns ~20 call sites for no behavioural gain, because every read
through a non-const document selects that overload too. Documented in the header
as a candidate M4 cleanup instead.

## Self Findings

Critical: none.

Major: none.

Minor:
1. `massPropertiesNode_` is hard-wired to whichever `BoxFeature` was added or
   restored most recently. Explicitly documented in ADR-M3-005 as a
   "first parametric solid" simplification and flagged for M4, not an accidental
   limitation. Not user-visible in M3, which has exactly one solid.
2. `Feature::recompute()` (the M1 no-context, bool-returning method) survives as
   vestigial on `BoxFeature`; the M3 engine path never calls it. Accepted debt
   under hard rule 8 in ADR-M3-004, with the M4 cleanup (collapsing `Feature`
   into `IRecomputable`) already named.
3. Deviation from spec 5's suggested layout: the kernel-neutral interface lives
   under `src/Core/Kernel/` rather than a top-level `src/Kernel/`. Declared and
   justified in ADR-M3-001 rather than done silently. `src/Kernel/Occt/` is
   exactly where the spec puts it.
4. `README.md` / `docs/Roadmap.md` / `AGENTS.md` still describe M3 as IN
   PROGRESS. Correct as of this report — they are updated at implementation-order
   step 18, after independent review, so that no document claims completion
   before it is earned. Worth 2 points on the reviewer scorecard and deliberately
   left outstanding here.

Zero-density policy: zero density is valid by documented decision (ADR-M3-004),
since COM derives from geometry and never divides by mass; negative and
non-finite densities fail. Recorded here so the reviewer scores it against the
stated policy rather than an assumed one.
